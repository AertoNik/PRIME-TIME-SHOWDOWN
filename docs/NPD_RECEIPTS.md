# Чеки НПД для PRIME SHOP — технические требования (Alpha 1.8.8)

> **Статус (23.10.2026): чеки НЕ формируются и НЕ имитируются.** Код игры и сервера не создаёт чеков, не показывает игроку «чек сформирован» и не хранит отметок о чеке: подтверждения от «Мой налог» у сервера нет. Сервис «Робочеки СМЗ» владельцем ещё не подключался и не проверялся. Документ — что должно быть сделано и проверено до первой настоящей продажи.

## 1. Что известно из открытых источников Robokassa (проверено 23.10.2026)

- **Робочеки СМЗ** — сервис Robokassa для самозанятых: подключается разрешением в приложении «Мой налог», после чего «автоматически активируется»; чек формируется на каждую оплату через Robokassa, отправляется покупателю и в ФНС, сохраняется в «Мой налог»; бесплатный; кассы не нужно ([robokassa.com/online-check/robochecksmz.php](https://robokassa.com/online-check/robochecksmz.php)). Для ИП на НПД — сначала заявка в поддержку.
- **Возврат:** по статье Robokassa ([как изменить или аннулировать чек самозанятого](https://robokassa.com/blog/articles/kak-izmenit-ili-annulirovat-chek-samozanyatogo/)) чек при возврате **не аннулируется автоматически** — продавец аннулирует его сам: в «Робочеки СМЗ» (история → «Аннулировать») или в «Мой налог» (раздел «Операции»). Причина «Возврат средств» — деньги вернули; «Чек сформирован ошибочно» — дохода не было (дубль, ошибка). Изменить чек нельзя — только аннулировать и при необходимости выдать новый (частичный возврат: аннулировать и выдать новый на оставшуюся сумму).
- **Номенклатура:** документация «Фискализация» ([docs.robokassa.ru/ru/fiscalization](https://docs.robokassa.ru/ru/fiscalization/)) говорит, что для «облачного решения, кассового решения или Робочеков» в запрос на платёж добавляется параметр `Receipt` (JSON): `items[].name` — до 128 символов без спецсимволов, `quantity`, `sum`, `tax` (обязателен; `none` — без НДС), `payment_method`, `payment_object`; `Receipt` URL-кодируется и входит в подпись `MerchantLogin:OutSum:InvId:Receipt:Пароль#1`. **Не сказано явно**, относится ли это к «Робочекам СМЗ» (самозанятые) или только к «Робочекам» для ИП/ООО, и откуда «Робочеки СМЗ» берут наименование, если `Receipt` нет (вероятно — из `Description`). **→ Отвечено поддержкой Robokassa: для «Робочеков СМЗ» `Receipt` обязателен, достаточно `name`, `quantity`, `sum`, `tax` (см. раздел 2).**
- **Сроки и ставки (422-ФЗ, по статье Robokassa — перепроверить):** при оплате картой/электронными деньгами — чек сразу после получения денег; ставка 4% для физлиц, 6% для ИП/юрлиц (для них в чеке нужны наименование и ИНН покупателя); лимит дохода НПД — 2,4 млн ₽ в год.

## 2. Что уже сделано в коде (и проверено тестами)

| Требование | Как сделано | Проверка |
|---|---|---|
| Наименование позиции понятно покупателю и называет предмет | Отдельное «чековое» название каждого товара (`receiptNameOf`, `src/config/shop.config.ts` → `receiptNames` в `backend/pb_hooks/lib/shop_rules.js`), хранится в заказе (`title`) | `npm run payments`: «order: … the receipt name kept» |
| Одно и то же название в окне Robokassa и в чеке | `Description` формы = название заказа; подготовленный `Receipt.items[0].name` — то же название | «the payment page names the item exactly as the order and the receipt will» |
| Название не искажается фильтром Robokassa и влезает в лимиты | Все 7 названий: 67–78 символов (лимит `Description` 100, `Receipt` 128), только буквы, цифры, пробел, `:` | «every receipt name … survives Robokassa's Description rule unchanged» |
| Сумма чека = сумма заказа = сумма оплаты | Одна позиция, количество 1; `OutSum` и `Receipt.sum` строятся из одной серверной цены в копейках | «prepared Receipt: … one item, the order sum, signed between InvId and the password» |
| Клиент не может изменить сумму или название | Цена и название — только с сервера (`checkout.js` → `payments.js`) | «4–6. order made: the SERVER price» |
| Учёт возвратов | `prime-shop refund` → `refund-done`: заказ `refunded`, право отозвано, отметка в журнале счетов | «refund confirmed → refunded; ONLY this order's right revoked» |
| Нет имитации фискализации | В базе нет полей «чек выдан», игра нигде не пишет «чек сформирован» | «no fiscal receipt is claimed in the game» (поиск по витрине и окнам покупки) |

**[УТВЕРДИТЬ владельцем / налоговым консультантом]** формулировки названий: «облик» и «предмет оформления» — косметика; LUCIEN назван «открытием игрового персонажа», т. к. это не косметика.

**Ответ поддержки Robokassa (письменно, магазин `primetimeshowdown`, «Робочеки СМЗ»):**

* `Receipt` **обязателен** для корректного формирования чеков.
* Для НПД достаточно `items` с полями `name`, `quantity`, `sum`, `tax`; `tax` = `none`.
* `sno`, `payment_method`, `payment_object` можно не передавать.
* `Receipt` входит в подпись SHA256 в URL-кодированном виде; в итоговом GET-адресе он кодируется дважды.
* Номенклатуру можно проверить заранее, раскрыв «Состав заказа» на платёжной странице.

**Alpha 1.8.9 — `Receipt` для НПД (локально, 27.10.2026; не развёрнуто, по умолчанию выключено — `ROBOKASSA_RECEIPT=on` в `/etc/primetime/robokassa.env`):**

* **Содержимое** — ровно подтверждённый набор, одна позиция: `{"items":[{"name":<название>,"quantity":1,"sum":<сумма>,"tax":"none"}]}`.
  * `name` — серверное название из `receiptNames` (то же, что в `Description`);
  * `sum` — сумма заказа в рублях, из тех же копеек, что `OutSum`.

  `sno`, `payment_method`, `payment_object` не передаются; переменной для `payment_object` больше нет.
* **Подпись.** `MerchantLogin:OutSum:InvId:Receipt:Пароль#1:Shp_*`, где `Receipt` — URL-кодированный минимизированный UTF-8 JSON (один раз). В поле формы — ровно тот же текст. Форма уходит POST как `application/x-www-form-urlencoded`: браузер кодирует поле второй раз — то же двойное кодирование, что в GET-ссылке. Robokassa раскодирует передачу и получает подписанный текст. ResultURL не меняется.
* **Тесты.** `npm run payments`: точный состав (только 4 поля), UTF-8, сумма = `OutSum`, подпись с `Shp_*`, двойное кодирование на проводе (POST и эквивалентный GET), разделение test и live, все 6 товаров, LUCIEN не продаётся. На временной базе — заказ с `Receipt` в тестовом режиме, тестовое уведомление, однократная выдача.
* **LIVE без `Receipt` — fail-closed.** При `PRIME_PAY_MODE=live` без `ROBOKASSA_RECEIPT=on` сервер не создаёт заказ и не выдаёт платёжную страницу (503 `receipt_required_for_live`; видно в `prime-shop status` и в предупреждении при запуске). Уже созданные заказы, ResultURL, возвраты и журнал счетов работают как раньше. DEMO и TEST не затронуты.
* **Ещё не подтверждено:** формируются ли чеки при `IsTest=1`. OpStateExt проверяет состояние платежа, а не чек. Чек НПД и запись дохода в «Мой налог» проверяются отдельно, при первой настоящей оплате.

## 3. Требования к процессу (что должно происходить при каждой продаже)

1. **Оплата подтверждена** (ResultURL с верной подписью) → предмет выдан сервером. Чек формирует Robokassa (Робочеки СМЗ) — независимо от нашего сервера.
2. **Покупатель получает чек** на email/телефон, указанный на странице Robokassa. Наш сервер email в форму не передаёт (`Email` не заполняется). **[РЕШЕНИЕ: передавать ли email PRIME ID для подстановки — это передача ПД платёжному сервису; отразить в Политике, если да]**
3. **Покупатель — физлицо** (ставка 4%). Покупки от ИП/юрлиц сервер не различает → оферта должна допускать только физлиц, либо нужен отдельный процесс (наименование и ИНН покупателя в чеке).
4. **Возврат** (полный): `prime-shop refund <InvId> reason="…"` → возврат денег в кабинете Robokassa (или Refund API) → `prime-shop refund-done <InvId>` → **вручную** аннулировать чек этой оплаты, причина «Возврат средств». Частичный: аннулировать и выдать новый чек на оставшуюся сумму в «Мой налог».
5. **Двойная оплата / неверная сумма / удалённый аккаунт** (заказ `requires_review`): вернуть деньги → аннулировать чек возвращённой оплаты («Возврат средств»).
6. **Тестовые и демонстрационные платежи** (staging и демонстрация на официальном сайте, `IsTest=1`) — не доход. Ожидание: чек не формируется. Проверить в «Мой налог» после первой демо-покупки (`docs/PRIME_DEMO.md`). Если всё же сформировался — аннулировать с причиной «Чек сформирован ошибочно» и сообщить в поддержку Robokassa.
7. **Сверка раз в месяц** (до 9-го числа следующего месяца — срок уплаты/сверки по НПД, перепроверить): операции Robokassa ↔ заказы `fulfilled`/`refunded` (`prime-shop orders 200`) ↔ чеки в «Мой налог». Связка — номер счёта (InvId), сумма, дата.
8. **Лимит 2,4 млн ₽/год** — следить в «Мой налог»; при приближении — закрыть продажи (`PRIME_SHOP_SALES=` пусто и перезапуск сервера — по отдельному решению).

## 4. Чего код не делает (и не должен притворяться)

- Не получает и не хранит ссылку на чек / номер чека (ResultURL их не содержит).
- Не аннулирует чеки (у «Робочеков СМЗ» нет такого API в использованных материалах).
- Не показывает игроку «чек отправлен». Окно покупки говорит только о статусе заказа и выдаче предмета.

## 5. Ручные шаги владельца (до продаж)

1. Спросить поддержку Robokassa (письменно): ~~(а) нужен ли `Receipt`; (б) какой `payment_object`~~ — отвечено (раздел 2: `Receipt` обязателен, `payment_object` не нужен); (в) формируются ли чеки по платежам с `IsTest=1`; (г) есть ли у «Робочеков СМЗ» уведомление/ссылка на чек, которые можно получать на сервер.
2. В кабинете Robokassa → раздел фискализации: подключить «Робочеки СМЗ» для магазина.
3. В приложении «Мой налог» → «Партнёры»: выдать разрешение Robokassa.
4. После активации live — **контрольная покупка владельцем** (настоящие деньги; отдельное решение): проверить чек в «Мой налог» (название, сумма, дата), что чек пришёл на email; затем при желании — возврат и аннулирование чека, чтобы отработать процесс.
5. Зафиксировать результаты в этом файле. `ROBOKASSA_RECEIPT=on` — включить на STAGING для тестовой оплаты (проверить «Состав заказа» на платёжной странице) и держать включённым в LIVE.
