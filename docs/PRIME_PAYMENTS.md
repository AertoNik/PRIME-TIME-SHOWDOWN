## 1. Как устроена покупка

```
PRIME SHOP → товар → PRIME CHECKOUT (этап 3)
  └─ «Перейти к оплате»
       1. сервер записывает согласие с офертой (consents, этап 3)
       2. POST /api/prime/shop/checkout {sku}: сервер заново проверяет товар, PRIME ID, документы,
          Люсьена, владение, цену, продажи, оферту, согласие, настройку оплаты —
          и создаёт заказ (или отдаёт уже открытый) + подписанную форму страницы Robokassa
       3. игра проверяет, что форма ведёт на https://auth.robokassa.ru/Merchant/Index.aspx, запоминает
          номер заказа (sessionStorage) и отправляет игрока на официальную страницу Robokassa
  └─ игрок платит на странице Robokassa (данные карты PRIME NETWORK не получает)
  └─ Robokassa → ResultURL сервера (сервер ↔ сервер):
       подпись (Пароль #2) → заказ → окружение → сумма → Shp_order →
       ОДНА транзакция: «оплачен» + право владения + «выдан» + журнал → ответ «OK{InvId}»
  └─ Robokassa → SuccessURL / FailURL сервера → 303 на игру с ?prime_pay=success|fail&inv=N
  └─ игра (после заставки) открывает PRIME SHOP → экран заказа → спрашивает сервер о заказе
       выдан + в списке прав аккаунта → «ПОКУПКА ПОДТВЕРЖДЕНА · ДОБРО ПОЖАЛОВАТЬ В PRIME COLLECTION»
       ещё нет → «Проверяем подтверждение оплаты…» (до ~47 с, 10 запросов) → «Подтверждение задерживается»
  └─ предмет — в «Моей коллекции» (скины, эффекты) или в составе (Люсьен); на любом устройстве после входа
```

Адрес возврата **ничего не доказывает** (SuccessURL — просто страница, FailURL даже не подписан): игра всегда спрашивает сервер. Товар выдаётся только после проверки уведомления ResultURL (или, в боевом режиме, положительного ответа Robokassa OpStateExt — см. §6).

## 3. Окружения — тест никогда не владеет в production

Две настройки сервера (в его env-файле, не в игре):

| | `PRIME_SERVER_ROLE` | `PRIME_PAY_MODE` | Пароли | Учитываемые права |
|---|---|---|---|---|
| Разработка | `dev` (только локальные скрипты) | `test` | случайные, придуманные на один запуск | `test` |
| Staging | `staging` | `test` (`IsTest=1`) | **только** тестовые #1/#2 | `test` |
| Production | `production` (или пусто) | `off` → `live` только по решению владельца | **только** боевые #1/#2 (+#3) | `live` |
| Демонстрация (официальный сайт) | `production` (репетиция — `staging`) | `demo` + обязательный `PRIME_DEMO_UNTIL` (≤ 92 дней) | **только** тестовые #1/#2 | `demo` (пока демонстрация идёт) |

Правила (`config()` в `lib/payments.js`; любое нарушение → оплаты нет вообще, без «запасного» режима):

- `test` на production (в т. ч. при пустой роли) → `test_on_production`; `live` вне production → `live_outside_production`.
- Тестовый сервер, на котором задан хоть один боевой пароль → `live_secrets_on_test_server`; боевой с тестовым → `test_secrets_on_live_server`.
- Нет логина магазина, алгоритма, пароля, пароли #1 и #2 совпадают, алгоритм не поддерживается → оплаты нет.
- Production **учитывает только `live`-права**: даже если тестовая запись каким-то образом окажется в базе production, она ничего не открывает (проверено на одной и той же базе).
- Номера счетов не пересекаются и не повторяются: боевые `10 000 000 000 + 10 × (секунды с 01.01.2026)`, тестовые `500 000 000 000 000 + …`, демонстрационные `700 000 000 000 000 + …` — выше всех номеров первой схемы (`1 000 001…` / `900 000 001…`); следующий номер = max(последний в базе + 1, отметка журнала + 1, «часы») — §6А.
- Боевое уведомление с `IsTest=1` отклоняется; тестовое с `IsTest=0` — тоже (флаг не подписан, поэтому он может только запретить).
- Подписи разных режимов не подходят друг к другу (разные пароли): тестовая форма не пройдёт как боевая.
- Локальный эмулятор платёжной страницы (`PRIME_PAY_DEV_GATEWAY`) принимается только при роли `dev` и только на `127.0.0.1`; staging и production всегда ведут на `https://auth.robokassa.ru/Merchant/Index.aspx`.

Цены: live — `prices` (утверждённые владельцем, сейчас все `null`); test — `test.prices` (10 ₽, только на staging; помечены «тестовый платёж»). Оферта: live — опубликованные редакции (сейчас нет); test — «Тестовые условия оплаты» (редакция 9001, документа нет, игрок отмечает «Я понимаю, что это тестовая оплата…»). Продажи: live — флаг релиза **и** `PRIME_SHOP_SALES=open`; test — `PRIME_SHOP_SALES=open` на staging.

## 4. Схема данных (PocketBase)

Все три коллекции **без API-правил**: игроки не читают, не создают, не меняют и не удаляют записи через общий API (проверено: 403). Пишут только маршруты hooks (владелец — сессия) и консольная команда администратора.

**`shop_orders`** — заказ: `user` (не обязательное, без каскада), `invId` (уникальный), `env` (test|live), `provider`, `sku`, `item`, `kind`, `title` (название на момент заказа), `amountKop` (целые копейки, фиксируется при создании), `currency` (RUB), `offerRevision`, `offerHash`, `status`, `hashAlg`, `expiresAt`, `paidAt`, `fulfilledAt`, `refundedAt`, `lastCheckAt`, `paidSum` (OutSum ровно как пришёл), `paidVia` (result|opstate), `opKey`, `paymentMethod`, `incCurrLabel`, `fee`, `reviewReason`, `refundKop`, `refundRequestId`, `note`, `created`, `updated`. **Не хранится:** данные карты, email плательщика из Robokassa.
Индексы: уникальный `invId`; **уникальный (`user`, `sku`, `env`) при `status = 'pending_payment'`** — один открытый заказ на аккаунт, товар и окружение; `(user, created)`, `(status, updated)`.

**`shop_entitlements`** — право владения: `user` (каскад), `sku`, `item`, `kind`, `order`, `source` (purchase|support), `env`, `status` (active|revoked), `grantedAt`, `revokedAt`, `revokeReason`.
Индексы: **уникальный `order`** (одно право на заказ — повтор уведомления не выдаст второе), **уникальный (`user`, `sku`, `env`) при `status = 'active'`**.

**`shop_payment_events`** — журнал: `order`, `invId`, `env`, `kind` (order_created, paid, fulfilled, review, result_refused, result_orphan, success_return, fail_return, expired, canceled, failed, refund_*, revoked, admin), `code`, `detail`, `created`. Без паролей, подписей, email, карт.

Согласие с офертой — существующая `consents` (этап 3), не дублируется.

Миграция только добавляет (аккаунты, профили, сохранения, история, сессии, приглашения и согласия не трогаются), откатывается и применяется заново (проверено). На настоящую базу **не применялась**.

## 5. Жизненный цикл заказа

```
pending_payment ──(проверенная оплата)──► paid ──► fulfilled ──► refund_pending ──► refunded
      │                                    │                           │
      ├─► expired  (не оплачен вовремя)     └─► requires_review          └─► fulfilled / requires_review
      ├─► canceled (заменён / аккаунт удалён / администратор)               (возврат не состоялся)
      └─► failed   (Robokassa: state 10 / 60, только live)
expired / canceled / failed ──(поздняя проверенная оплата)──► paid → fulfilled | requires_review
```

Переходы заданы таблицей `NEXT` в `lib/payments.js`: любой другой бросает исключение внутри транзакции (ничего не записывается наполовину). В «оплачен» заказ попадает **только** из проверенного уведомления ResultURL или ответа OpStateExt — ни клиентский запрос, ни SuccessURL туда не ведут. Из `refunded` выхода нет. История не стирается.

- **Срок заказа** — 2 часа (`ORDER_TTL_MS`), тот же срок уходит в Robokassa (`ExpirationDate`, московское время — безопасное прочтение: если Robokassa читает его как UTC, страница просто будет открыта на 3 часа дольше). Через 15 минут после срока неоплаченный заказ закрывается (`expired`, cron каждые 5 минут).
- **Повторное нажатие / две вкладки / два устройства** — тот же открытый заказ: тот же InvId, та же подпись (уникальный индекс + сериализованные транзакции; проверено 8 параллельными запросами). Robokassa не принимает второй платёж по одному InvId (ошибка 40) — двойного списания из-за двойного нажатия нет. Важно: в тестовом режиме Robokassa ошибку 40 не выдаёт — повторная тестовая оплата того же счёта возможна, но второе право не выдаётся.
- **Зависший заказ не блокирует**: после срока следующий «Купить» создаёт новый заказ; изменилась цена или редакция оферты — старый открытый заказ закрывается (`canceled`), создаётся новый по новым условиям.
- **Лимит**: не больше 20 новых заказов на аккаунт в час (повторно выданный заказ не считается).
- **Поздняя оплата** закрытого заказа (вкладка закрыта, уведомление пришло позже): деньги взяты — заказ «оплачен» и выдаётся; если предмет уже есть (заплатили второй раз) — `requires_review` (`already_owned`), администратор возвращает деньги.

## 6. Подписи и ResultURL

Формулы (официальная документация, `pay-interface`, `notifications-and-redirects`, OpenAPI 1.3.0):

| Где | Строка | Пароль |
|---|---|---|
| Форма оплаты | `MerchantLogin:OutSum:InvId[:Receipt]:Пароль#1[:Shp_k=v…]` | #1 (тестовый на staging) |
| ResultURL | `OutSum:InvId:Пароль#2[:Shp_k=v…]` — OutSum **ровно как пришёл** («149.000000» боевой, «149.00» тестовый) | #2 |
| SuccessURL | `OutSum:InvId:Пароль#1[:Shp…]` — не используется для решений | #1 |
| OpStateExt | `MerchantLogin:InvoiceID:Пароль#2` | #2 (только боевой) |

`Shp_*` сортируются по имени. Мы передаём один: `Shp_order` = id заказа в базе — связывает InvId с заказом (подменить нельзя: он в подписи). `IsTest` не входит в подпись. Сравнение подписи — без утечки по времени (`$security.equal`), регистр hex не важен.

**Алгоритм** задаётся `ROBOKASSA_HASH_ALGORITHM` (md5 | sha256 | sha512) и **никогда не угадывается**: пусто → оплаты нет. Он один для основных и тестовых паролей (документация testing-mode). RIPEMD160, SHA1, SHA384 PocketBase не вычисляет — сервер с ними оплату не включит. Если подпись уведомления не совпала, но совпала бы с другим алгоритмом или с Паролем #1, в журнал сервера пишется подсказка (`algorithm:md5`, `password1`) — уведомление всё равно отклоняется. Это помогает при первом тестовом платеже.

**ResultURL, шаги** (`result()`):
1. оплата настроена (иначе 503 — Robokassa повторит позже); необязательный список IP (`ROBOKASSA_RESULT_IPS`);
2. параметры читаются из **исходного текста** запроса (стандартный разбор PocketBase превращает «123» в число и «0.5» в 0.5 — подпись бы не сошлась; обнаружено и проверено);
3. обязательные поля, InvId — число, OutSum — сумма, подпись — hex;
4. `IsTest` не противоречит режиму;
5. подпись Паролем #2 выбранным алгоритмом;
6. заказ по InvId существует; если нет (база восстановлена из старой копии) — заказ **восстанавливается из журнала счетов** с тем же id, но только когда `Shp_order` и сумма совпадают с записью журнала; иначе 404 и запись `result_orphan`;
7. окружение заказа = режим сервера; `Shp_order` = id заказа;
8. состояние: уже выдан / на возврате / на проверке → «OK» без изменений (повтор); оплачен, но не выдан → выдать;
9. **одна транзакция**: «оплачен» (+ OutSum, способ, комиссия) → сумма = сумме заказа (в копейках; иначе `requires_review: amount_mismatch`, ничего не выдаётся) → право владения → «выдан» → журнал;
10. ответ `OK{InvId}` — **только после** фиксации.

Если шаг выдачи упал (ошибка базы) — транзакция откатывается целиком, затем отдельной транзакцией сохраняется хотя бы «оплачен» и отвечается «OK»: деньги не теряются, предмет выдаст cron (5 мин), запуск сервера или запрос игры о заказе. Если не удалось сохранить даже оплату — ответ 500, Robokassa повторит уведомление.

**Поздние уведомления и сверка (только live):** заказы без уведомления дольше 3 минут сервер спрашивает у Robokassa (OpStateExt, не чаще раза в 10 минут; по кнопке игрока «Проверить ещё раз» — не чаще раза в 30 секунд на заказ). Только **положительный полный ответ** (state 100 и сумма заказа) **этого заказа** засчитывается как оплата: в `UserFields` операции должен быть `Shp_order` = id заказа, а время операции (`StateDate`) — не раньше создания заказа (минус 10 минут на часы); старая оплата под тем же номером ничего не оплачивает (запись `opstate_unbound`); state 10/60 → `failed`; отсутствие ответа ничего не меняет. В тестовом режиме OpStateExt не работает (документация) — там только ResultURL.

## 6А. Журнал счетов вне базы и восстановление из копии

**Проблема (аудит):** номер счёта брался как «последний в базе + 1». После восстановления старой копии `pb_data` номера пошли бы заново — Robokassa уже видела их (оплата — ошибка 40), а оплаты, подтверждённые после копии, пропали бы вместе с заказами.

**Решение** (`lib/ledger.js`, `lib/payments.js`):
- Каталог `prime-ledger/<env>/` **рядом с** `pb_data` (или `PRIME_LEDGER_DIR`): `mark` — наибольший выданный номер; `<InvId>.json` — заказ (id = `Shp_order`, аккаунт, товар, сумма, оферта, название, время) + позже `paid` и `refunded`. Файлы 0600, запись атомарная (временный файл + переименование). `restore.sh` заменяет `pb_data`, но не этот каталог.
- **Номер резервируется в журнале ДО подписи страницы оплаты**: не удалось записать → заказа нет (503 `ledger_unavailable`); журнал не читается (повреждена отметка) → оплата выключена (`payments off — ledger_unavailable`). Номер никогда не угадывается.
- Следующий номер = max(последний в базе + 1, `mark` + 1, нижняя граница по часам). Часы — третья страховка (если пропали и база, и журнал); база и журнал страхуют от переведённых назад часов.
- Каждая проверенная оплата и каждый подтверждённый возврат отмечаются в журнале.
- **При каждом старте** (`recover`, также `prime-shop recover`): оплаченный по журналу заказ, которого нет в базе, восстанавливается с тем же id и выдаётся; возврат, которого база «не помнит», выполняется снова (право отзывается). Повторный запуск ничего не меняет. Расхождение номера (в базе другой заказ под этим номером) — не трогается, пишется в журнал сервера.
- Удаление аккаунта убирает его id и из журнала (записи остаются без человека — как заказы в базе).
- `backup.sh` кладёт журнал (и заметку об удалённых аккаунтах) в каждый архив; `restore.sh` **объединяет**: добавляет недостающие файлы, отметка — большая из двух; показывает аккаунты/сохранения/заказы архива и текущей базы до замены; предупреждает, если включены боевые платежи.
- `prime-shop ledger` — каталог, отметка против последнего номера в базе, следующий номер, «оплачены, но нет в базе».

Проверено (`npm run payments`, раздел «Восстановление старой копии»): настоящие `backup.sh` → оплата, неоплаченный заказ и возврат после копии → `restore.sh` → старт: заказ восстановлен и выдан, возврат повторён, уведомление по заказу, которого нет в базе, восстанавливает его и выдаёт, подделка `Shp_order`/суммы — отказ; новый номер выше всех прежних; аккаунты и сохранения на месте.

## 7. Выдача и права в игре

- Право создаётся сервером в транзакции оплаты; источник `purchase` (или `support`, если администратор вручную завершил заказ на проверке).
- `GET /api/prime/shop/purchases` — купленное этим PRIME ID и последние заказы; `GET /api/prime/shop/orders/{inv}` — свой заказ (чужой → 404); `GET /api/prime/shop/status` — также `owned`, `env`, цены, открытые заказы.
- Игра (`AccountRuntime.refreshRights`): права **только вошедшего PRIME ID** и только пока играется его карьера (или гостевая на этом устройстве). Сменился аккаунт или выход — список **сразу** очищается, потом читается заново; поздний ответ для прежнего аккаунта отбрасывается. На устройстве список не хранится (подделать `localStorage` бесполезно); без связи купленное ждёт сервер.
- Сохранение покупок не хранит: `save.shop` — только выбор надетого; сервер отклоняет сохранения с платными предметами в `cosmetics.owned` (этап 2).
- **Люсьен** после сезона: право `fighter_lucien` открывает его в составе (`inRoster`), но `fighters.lucien.unlocked` в сохранении остаётся `false`. Его можно выбрать — сервер PRIME CLOUD разрешает `selected: 'lucien'` только аккаунту с правом на него. Если права нет (возврат, другой аккаунт), игра, получив ответ сервера, переводит выбор на Рэя; в бою без подтверждённого права играет Рэй. Люсьен, открытый за жетоны, не зависит от покупок: возврат его не трогает. Повторно за рубли он не продаётся (сохранение + реестр), в сезон — только за жетоны.
- Карьерный прогресс (этапы, счётчики подписанных бойцов) по-прежнему считает только сохранение — покупка его не двигает.

## 8. Экраны (PRIME CHECKOUT)

Подробно — `docs/PRIME_CHECKOUT.md` §12. Кратко: «Тестовый платёж» везде, где staging; «Переходим на страницу оплаты Robokassa…»; «Страница оплаты не открылась» (тот же заказ, «Повторить оплату»); «Проверяем подтверждение оплаты…» → «Подтверждение задерживается» (без бесконечных запросов); «Оплата не завершена» (заказ сохранён, второго списания не будет); «Заказ ожидает оплаты» → «Продолжить оплату»; «Заказ закрыт» → «Оформить заново»; «Покупка на проверке» → «Написать в поддержку» (официальный адрес primetimeshowdown.official@gmail.com с номером заказа); «Оформляется возврат» / «Возврат выполнен»; **«ПОКУПКА ПОДТВЕРЖДЕНА · ДОБРО ПОЖАЛОВАТЬ В PRIME COLLECTION»** — только для заказа «выдан» + право в списке сервера; кнопка «В мою коллекцию» (гардероб) или «В мой состав» (Люсьен). Анимации отключаются при `prefers-reduced-motion` и настройке движения в игре.

Политика безопасности страницы (CSP) разрешает отправлять формы **только** на `https://auth.robokassa.ru` (раньше `form-action 'none'` заблокировал бы переход к оплате — найдено при проверке в браузере). Сервер разработки дополнительно разрешает `http://127.0.0.1:*` для эмулятора; в production-сборке этого нет (`npm run payments` проверяет `dist/`).

## 8А. Возврат с Robokassa — без белой страницы

- `PRIME_GAME_URL` нормализуется: `https://…` где угодно, `http://` только для `localhost` / `127.0.0.1` / `[::1]`; без пути или с папкой в конце — добавляется `/` (`https://primetimeshowdown.online` → `…online/`), `#…` отбрасывается. SuccessURL/FailURL → 303 на `<адрес>?prime_pay=success|fail&inv=N`.
- Адреса нет или он неверный → вместо пустой страницы — страница в стиле PRIME («Проверяем оплату» / «Оплата не завершена», номер заказа) с кнопкой «Вернуться в игру»; на production кнопка ведёт на официальный сайт, на других серверах — подсказка про `PRIME_GAME_URL`. Страница ничего не обещает: решает сервер. При старте сервер пишет адрес и предупреждение, если он неверный при включённой оплате; `prime-shop status` показывает его.
- Игра: после возврата на заставке — «PRIME SHOP · заказ №N: нажмите, чтобы проверить покупку»; затем экран заказа спрашивает сервер (экран «ПОКУПКА ПОДТВЕРЖДЕНА» — только при `fulfilled` + право в списке сервера).
- Оплата в **новой вкладке** («Открыть в новой вкладке» при «Страница оплаты не открылась»): та же подписанная форма (тот же счёт, второго заказа нет), отправляется прямо в нажатии (без запроса — браузер не блокирует), `target=_blank`, `rel=noopener`. Исходная вкладка показывает «Оплата открыта в новой вкладке» и проверяет заказ, когда игрок к ней возвращается (`visibilitychange`/`focus`) или когда другая вкладка игры подтвердила заказ (`BroadcastChannel` + событие `storage`; сигнал несёт только номер — вкладка сама спрашивает сервер).

## 9. Возвраты и отзыв права

Только администратор, только на сервере (`sudo bash deploy/linux/prime-shop.sh …` — обёртка над `pocketbase prime-shop …` с настройками сервера; для staging `PRIME_INSTANCE=staging`), никаких кнопок в игре:

| Команда | Что делает |
|---|---|
| `refund <InvId> [RUB] reason="…"` | заказ → `refund_pending`; **право ещё не отзывается** (деньги не вернулись) |
| `refund <InvId> … api` | то же + заявка в Refund API (только live, `ROBOKASSA_PASSWORD_3`, `PRIME_PAY_REFUND_API=on`; OpKey берётся из OpStateExt) |
| `refund-check <InvId>` | Refund API: `finished` → refunded + отзыв; `canceled` → назад; `processing` → ждать (cron проверяет сам) |
| `refund-done <InvId> [keep-item]` | деньги вернулись (возврат сделан в кабинете Robokassa): refunded; полный возврат отзывает право **этого заказа** |
| `refund-failed <InvId> [reason="…"]` | возврат не состоялся: заказ возвращается в `fulfilled` (или `requires_review`) |

Отзывается только право, созданное этим заказом: другие покупки и предметы, полученные игрой (Люсьен за жетоны, сезонные награды), не трогаются (проверено). Частичный возврат по умолчанию предмет не отзывает. Запрос возврата ≠ вернувшиеся деньги: заказ «возвращён» только после подтверждения.

Refund API: `POST https://services.robokassa.ru/RefundService/Refund/Create`, тело — JWT HS256 (Password3), `{OpKey, RefundSum?}`; состояние — `GET …/Refund/GetState?id=`. По OpenAPI Robokassa API возвратов нужно отдельно подключить магазину (без этого — 401), тестового режима у него нет. **Реальные возвраты не выполнялись**; токен проверен на эталоне (Node HMAC = PocketBase HMAC).

Прочие команды: `status` (настройки без секретов, счётчики), `selftest` (эталонные подписи на выдуманных паролях), `orders [N]`, `order <InvId>` (заказ, журнал, право), `reconcile [InvId]`, `deliver <InvId>`, `cancel <InvId>`, `review <InvId> deliver [note=…] | note <текст>`.

## 12. План безопасного развёртывания (выполняет владелец, по отдельному разрешению на каждый шаг)

1. **Проверка актуального сервера**: `sudo systemctl status pocketbase`, `curl -s https://api.primetimeshowdown.online/api/health`, версия файлов в `/opt/primetime`.
2. **Резервная копия**: `sudo systemctl start prime-backup` и `sudo journalctl -u prime-backup -n 5 --no-pager` (как в `docs/PRIME_CLOUD_DEPLOY.md`), затем `sudo bash deploy/linux/backup-check.sh` (после обновления до 1.8.8: `/opt/primetime/deploy/backup-check.sh`) + зашифрованная копия **вне VPS** (`docs/PRIME_CLOUD_BACKUP.md`, раздел 3) + копия `/etc/primetime/*.env` в личное хранилище.
3. **Миграции на копии**: `npm run backend:migrate-check -- <копия>` на своём компьютере — аккаунты, хеши паролей, профили, сохранения не меняются.
4. **Серверная логика 1.8.8 с выключенными платежами**: поднять версию (`src/config/version.ts`, `package.json`), `npm run backend:rules`, `npm run server:bundle` (новый архив; архив 1.8.4 не перезаписывается — команда откажется; **архив 1.8.8, собранный владельцем ранее (SHA 6290c08a…), устарел** после доработки 23.10.2026 — пересобрать с `-- --replace` или поднять версию, только по решению владельца), загрузить и выполнить `sudo bash deploy/linux/update.sh` из распакованного архива (как в `docs/PRIME_CLOUD_DEPLOY.md`). `PRIME_PAY_MODE` не задан → оплата выключена, `shop.payments: 1`. `update.sh` не меняет описание службы: строка `EnvironmentFile=-/etc/primetime/robokassa.env` понадобится только при активации (шаг 10: `sudo install -m 644 deploy/linux/pocketbase.service /etc/systemd/system/pocketbase.service && sudo systemctl daemon-reload`).
5. **PRIME ID**: вход, регистрация (по текущему режиму), подтверждение почты.
6. **PRIME CLOUD**: синхронизация, одна сессия, конфликты.
7. **Здоровье сервера**: `/api/health`, `journalctl -u pocketbase` (строка «PRIME: server role production, payments off»), `sudo bash deploy/linux/prime-shop.sh status`.
8. **Тестовая интеграция** — на отдельном staging (`docs/ROBOKASSA_SETUP.md`), не на production.
9. **Клиент** 1.8.8: `npm run build`, проверки, публикация на сайт (отдельное разрешение).
10. **Активация** — только после модерации магазина, утверждённых цен и документов: `ROBOKASSA_PASSWORD_1/2` в `/etc/primetime/robokassa.env`, `PRIME_SERVER_ROLE=production`, `PRIME_PAY_MODE=live`, цены и `SHOP_SALES_OPEN` в релизе, `PRIME_SHOP_SALES=open`, контрольная покупка владельцем, проверка чека.
