# PRIME PAYMENTS — безопасность (Alpha 1.8.8, этап 4)

Короткий разбор: что может пойти не так и что этому мешает. Подробности устройства — `docs/PRIME_PAYMENTS.md`. Каждая строка таблицы проверяется автоматически (`npm run payments`, если не сказано иное).

## Угрозы и защита

| Угроза | Защита |
|---|---|
| Игрок меняет цену в запросе | Браузер отправляет только `{sku}`; цена — из `shop_rules.js` сервера в целых копейках, фиксируется в заказе. Поля `price`, `priceKop`, `amountKop`, `status`, `paid` в запросе игнорируются |
| Игрок покупает «за другой аккаунт» / присваивает чужую покупку | Владелец заказа и права — аккаунт из сессии (`user`, `accountId` в запросе игнорируются); чужой заказ → 404; права читаются только своим PRIME ID |
| Подделка уведомления об оплате | Подпись ResultURL с Паролем #2 (только на сервере), сравнение без утечки по времени; подменить OutSum, InvId или `Shp_order` нельзя — они в подписи |
| Неверный алгоритм / пароль в настройке | Неверная подпись всегда отклоняется; подсказка (`algorithm:…`, `password1`) — только в журнал сервера |
| Тестовая оплата открывает предмет в production | Роль сервера + режим оплаты; на тестовом сервере нет боевых паролей и наоборот; production учитывает только `live`-права; `IsTest=1` на production отклоняется; разные диапазоны InvId (live от 10¹⁰, test от 5·10¹⁴) и разные журналы счетов |
| Продажа по неутверждённой цене | Утверждение — по каждому товару (`SHOP_PRICE_STATUS`): неутверждённая цена (LUCIEN) не попадает на сервер — `price_pending`, «Цена уточняется». Утверждённые цены сами продаж не открывают: на полностью настроенном боевом сервере с настоящими правилами 1.8.8 — `sales_closed` |
| Демонстрация превращается в бесплатную раздачу настоящих прав | Отдельное окружение `demo`: свои права, журнал и диапазон счетов; учитываются только пока демонстрация идёт (обязательный последний день ≤ 92 дней); боевой режим их не учитывает; `prime-shop demo-end` отзывает. Персонажи в демонстрации не продаются |
| Демонстрация проводит настоящий платёж | В режиме `demo` сервер держит только тестовые пароли (с боевым — оплата выключена), всегда `IsTest=1`; уведомление с `IsTest=0` или боевой подписью отклоняется |
| Тестовый режим «просачивается» на production | `test` на production по-прежнему запрещён; `demo` — отдельный явный режим со своим сроком; браузер режим не выбирает |
| Передача счетов staging через production | Только тестовый диапазон, только на адрес из настройки сервера (https или 127.0.0.1), без изменений и без решений на production; повторная передача — 508; не-production не передаёт |
| Ошибка настройки включает «боевой» режим | Любая неясность → оплаты нет. Пустая роль = production, где тестовый режим запрещён. Запасных режимов нет |
| Повторное уведомление выдаёт второй предмет | Состояние заказа + уникальный индекс права на заказ; повтор отвечает «OK» без изменений |
| Два уведомления одновременно | Транзакции PocketBase выполняются по очереди + уникальные индексы (проверено 6 одновременными) |
| Двойное нажатие «Купить» → два платежа | Один открытый заказ на аккаунт/товар/окружение (уникальный индекс), повтор отдаёт тот же InvId; Robokassa не принимает вторую оплату того же InvId |
| Уведомление пришло, а запись выдачи упала | Транзакция откатывается целиком; отдельно сохраняется «оплачен»; выдача повторяется cron, при старте сервера и при запросе игры |
| Сервер перезапустился посреди обработки | Транзакция SQLite атомарна; без «OK» Robokassa повторит уведомление; оплаченные, но не выданные заказы выдаются при старте |
| Оплата после закрытия вкладки / поздно | Проверенная оплата закрытого заказа засчитывается; права приходят при следующем входе |
| Заплатили дважды за один предмет | Второй заказ → `requires_review` (`already_owned`), без второго права; возврат — администратор |
| Сумма в уведомлении другая | `requires_review` (`amount_mismatch`), ничего не выдаётся |
| Восстановили старую копию базы → номера счетов пошли заново (Robokassa уже видела их; ошибка 40, чужая старая оплата) | Журнал счетов **вне базы** (`prime-ledger/`): номер резервируется в нём до подписи страницы; следующий номер = max(база + 1, отметка журнала + 1, часы); `restore.sh` журнал объединяет, а не откатывает. Журнал недоступен → заказа нет (503) / оплата выключена — номер никогда не угадывается |
| Оплата или возврат после копии пропали при восстановлении | Отметки `paid`/`refunded` в журнале; при старте (`recover`) оплаченный заказ восстанавливается с тем же id и выдаётся, возврат повторяется (право отзывается); повторный запуск ничего не меняет |
| Уведомление для заказа, которого нет в базе | Восстанавливается из журнала, **только** если `Shp_order` и сумма совпадают с записью; иначе 404 (не «OK»), запись `result_orphan` для администратора |
| Ответ OpStateExt про **старую** оплату под тем же номером засчитывается новому заказу | Засчитывается только операция этого заказа: `Shp_order` в `UserFields` = id заказа и `StateDate` не раньше создания заказа; иначе `opstate_unbound`, ничего не выдаётся |
| Подделка SuccessURL (`?prime_pay=success`) | Адрес возврата только говорит игре, какой заказ проверить; успех — только по ответу сервера (заказ выдан + право в списке) |
| Открытый редирект через SuccessURL / FailURL | Адрес возврата — из настройки сервера `PRIME_GAME_URL`, не из запроса |
| Белая страница после оплаты (неверный `PRIME_GAME_URL`) | Адрес нормализуется (`/` в конце, только https или localhost); неверный → оформленная страница «Проверяем оплату» с кнопкой (production — официальный сайт), предупреждение в журнале при старте; страница ничего не выдаёт и не обещает |
| Оплата в новой вкладке создаёт второй заказ / второй платёж | Новая вкладка получает ту же подписанную форму (тот же InvId); сигнал между вкладками несёт только номер заказа — каждая вкладка спрашивает сервер сама |
| Правка `localStorage` / сохранения открывает платное | Права не хранятся на устройстве и в сохранении; сервер отклоняет сохранения с платными предметами; надетый, но не купленный предмет не показывается |
| Права одного PRIME ID видны другому | Список очищается сразу при смене аккаунта или выходе; поздний ответ прежнему аккаунту отбрасывается |
| Игрок пишет в заказы/права через общий API | У коллекций нет API-правил (403 на чтение, создание, изменение, удаление) |
| «Кнопка выдать / подтвердить оплату / вернуть деньги» | Нет в игре и в API. Ручные действия — только консольная команда на сервере (доступ по SSH) |
| Утечка паролей Robokassa | Только в env-файлах сервера (`/etc/primetime*/robokassa.env`, права 640); никогда в игре (`dist/` проверяется), в ответах API, в журналах (проверяется весь журнал прогона), в выводе `prime-shop status` |
| Форма уходит не на Robokassa | Игра принимает только `https://auth.robokassa.ru/Merchant/Index.aspx` и поля Robokassa; CSP страницы разрешает формы только на `https://auth.robokassa.ru` (эмулятор `127.0.0.1` — только в `npm run dev`) |
| Данные карты | Не запрашиваются и не хранятся: оплата — на странице Robokassa. В заказе — способ оплаты, комиссия, OutSum; email плательщика не сохраняется |
| Перебор / засорение | Лимиты PocketBase: `/api/prime/pay/` 120 в минуту, `/api/prime/shop/` 30 в минуту; не больше 20 новых заказов на аккаунт в час; отказы для неизвестных заказов не пишутся в журнал заказов |
| Бесконечные запросы из браузера | После возврата — не больше 10 запросов за ~47 с, затем «Подтверждение задерживается» и кнопка «Проверить ещё раз» |
| Возврат отнимает чужое или независимое | Отзывается только право, созданное этим заказом; Люсьен за жетоны (сохранение) и другие покупки не трогаются; заявка на возврат ≠ возврат — право отзывается только после подтверждения |
| Удаление PRIME ID | Права удаляются вместе с аккаунтом; открытые заказы закрываются; заказы остаются без связи с человеком (финансовая запись); оплата, пришедшая после удаления, — на проверку |

## Что не проверено и требует staging

- Настоящее уведомление Robokassa: фактические поля (`IsTest`, `Fee`, `EMail`, дополнительные поля), формат OutSum в тестовом и боевом режимах.
- `ExpirationDate` (часовой пояс не указан в документации).
- OpStateExt и Refund API против серверов Robokassa (у OpStateExt нет тестового режима, у Refund API — тоже; по OpenAPI API возвратов подключается магазину отдельно).
- Список IP Robokassa (`ROBOKASSA_RESULT_IPS`) — по умолчанию не ограничен, решает подпись.

## Правила для разработки

- Подпись считает только сервер (`lib/robokassa.js`); в `src/` нет паролей, алгоритмов подписи платежа и названий переменных Robokassa (`npm run payments`).
- Параметры уведомления читаются из исходного текста запроса (`RK.parseForm`), не через стандартный разбор PocketBase: тот превращает «123» в число и ломает подпись.
- Переходы состояния заказа — только через `move()` и таблицу `NEXT`.
- Новые способы выдачи — только через `fulfillTx` в транзакции оплаты (или `review … deliver` администратора).
- Тестовые проверки используют случайные выдуманные пароли и временные базы; настоящие секреты в репозиторий не попадают.
