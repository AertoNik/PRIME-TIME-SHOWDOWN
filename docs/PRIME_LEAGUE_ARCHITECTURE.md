## 2. Главный вопрос: можно ли доказать исход боя на сервере — **ДА** (проверено)

**Модель: сервер сам переигрывает бой.**

1. Сервер создаёт матч: свой случайный `seed`, снимок обеих сторон (боец, колода, тактика ИИ, уровень, арена), версия правил боя `SIM_VERSION`.
2. Клиент ведёт тот же `Match` с этим `seed` и записывает **только нажатия**: `[шаг, номер карты в руке]` (плюс сдача).
3. В конце клиент присылает журнал нажатий. Сервер запускает **тот же код боя** (сборка `src/combat` → `pb_hooks/lib/league_sim.js`) и сам получает победителя, HP, рейтинг эфира. Присланный клиентом исход не принимается — его просто нет в протоколе.

Подделать нечего: журнал нажатий — это и есть игра. Невозможное нажатие (нет энергии, карта на перезарядке, не та фаза) сервер так же отклонит, как игра. Чужая колода, другой seed, другая арена — в снимке на сервере, клиент их не присылает.

### Детерминизм между движками — найден и устранён реальный барьер

| Проверка | Итог |
|---|---|
| Node (V8): 40 боёв бота, переигранных из журнала нажатий | 40/40 побитово одинаково |
| PocketBase goja, **до** исправления | 0/40: расхождение на 5–9-й секунде боя, в 1 случае другой победитель |
| Причина | `Math.hypot/atan2/sin/cos/exp` в V8 и Go округляют последний бит по-разному; бой хаотичен |
| Исправление | `src/core/dmath.ts`: те же функции из `+ − × ÷ √` (алгоритмы fdlibm) — IEEE 754 даёт одинаковые биты везде. Точность ≤ 1 ulp (2 млн проверок) |
| PocketBase goja, **после** | **40/40 побитово** (хеш состояния на каждой секунде и исход) — 5 арен, 7 бойцов, 3 сложности |
| Цена на сервере | goja: медиана ≈ 1,1 с на бой (0,6–5 с), Node ≈ 40 мс. Один пересчёт на матч — приемлемо для текущей аудитории; для роста — отдельный Node-проверяющий (раздел 6) |

### Что остаётся ограничением (честно)

- **Помощь программы при игре.** Seed нужен клиенту для показа боя, поэтому бот на стороне игрока может перебирать варианты нажатий (как движок в онлайн-шахматах). Меры: один seed на матч, матч нельзя начать заново, минимальная длительность в реальном времени, лимит частоты нажатий, сравнение по статистике позже. Полностью исключить нельзя ни в одной игре с клиентской симуляцией.
- **Владение из карьеры.** Открытие бойцов и карт за $ считает клиент; сервер видит облачное сохранение, а не доказательство заработка. Поэтому лига принимает только настоящих бойцов и карты каталога, не боссов и NPC, а рубли (LUCIEN) — по `shop_entitlements`. Изменённое сохранение может открыть набор раньше, но **не создаёт силы сверх каталога**: бойцы симметричны, косметика не влияет на бой. Полное устранение — серверная экономика карьеры (вне 1.9.0).
- **Версия правил.** Матч помнит `SIM_VERSION`; если сервер обновился посреди матча, такой матч **аннулируется без RP** (не пересчитывается по новым правилам).

## 3. Жизненный цикл матча

```
start (сервер: seed, снимок, SIM_VERSION, срок) → бой у клиента (журнал нажатий; каждые ~10 с промежуточная отправка)
  → finish (журнал) → пересчёт → в одной транзакции: статус active→done, RP/MMR, токены, статистика защиты
  ↘ клиент пропал: по сроку cron переигрывает то, что было прислано (дальше боец бьётся без карт) → обычная финализация
  ↘ сервер обновил правила боя → void (без RP)
```

- **Идемпотентность:** финализация проверяет `status = 'active'` внутри транзакции; второй запрос/вкладка получает уже записанный итог. Один активный матч на аккаунт — уникальный частичный индекс.
- **Обрыв связи:** не бесплатная отмена и не автоматическое поражение — бой досчитывается по присланным нажатиям.
- **Сдача** — явное нажатие «сдаться» в журнале (поражение).
- **Слишком ранняя отправка** (раньше, чем мог длиться бой в реальном времени) — отказ `too_early`.

## 4. Данные (миграция `1793100000_prime_league.js`, только добавление)

| Коллекция | Назначение | Уникальность |
|---|---|---|
| `league_profiles` | участник: сезон, RP, MMR, ранг, вызов, токены, статистика, принятая версия правил, защита вкл/выкл | `owner` |
| `league_defense` | 1–5 слотов: боец, колода, тактика, уровень, облик, вкл., версия, статистика | `(owner, slot)`, `(owner, fighter)` |
| `league_matches` | матч: режим, стороны, снимок, seed, SIM_VERSION, журнал, срок, исход, начисления | один `active` на атакующего |
| `league_ledger` | токены: приход/расход с основанием | `(owner, reason, ref)` |
| `league_series` | RUSH / SQUAD / CHALLENGE: состояние серии | один активный на `(owner, kind)` |
| `league_history` | архив сезона на участника | `(owner, season)` |
| `league_rewards` | полученные награды дорожки сезона | `(owner, season, tier)` |
| `league_upgrades` | уровни бойцов за токены (под флагом) | `(owner, fighter)` |

Ни у одной коллекции нет API-правил: всё только через маршруты `/api/prime/league/*`. Удаление PRIME ID удаляет лиговые записи каскадом. Платёжные коллекции, сохранения, `shop_entitlements`, оферта и возрастные правила **не меняются**.

## 6. Нагрузка

Один пересчёт ≈ 1 с процессора на сервере (goja). При 5–50 одновременно активных игроках это допустимо: бой длится ~80 с, пересчёт один. Если лига вырастет: (1) отдельный процесс Node на том же сервере (тот же файл `league_sim.js`, ×30 быстрее) или (2) очередь проверки с ответом «результат подтверждается». Решение — до массового запуска.
