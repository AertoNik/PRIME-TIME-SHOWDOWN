# Alpha 1.8.3 «PRIME CLOUD 2.0» — как обновить сервер и сайт

> Ничего из этого не выполнено автоматически. Сервер Timeweb и GitHub Pages обновляются **только вами**, по шагам ниже, после вашего решения.

Сайт: https://aertonik.github.io/PRIME-TIME-SHOWDOWN/
Сервер: https://primetime-showdown-beta.duckdns.org

Команды с `$` в начале строки выполняются **на сервере** (по SSH), без самого `$`. Остальные — на Mac, в папке `PRIME TIME Duel`.

---

## 1. Что меняется (простыми словами)

- **Один PRIME ID — одна активная игра.** Открыли игру на компьютере — играет компьютер. Телефон, другая вкладка или браузер показывают «PRIME ID ОТКРЫТ НА ДРУГОМ УСТРОЙСТВЕ» и кнопку «Продолжить здесь». Старая вкладка сама управление не забирает, поэтому бесконечного перехвата не бывает.
- **Прогресс приезжает сам.** При открытии игры аккаунт загружается из PRIME CLOUD автоматически. Импорт и выбор сохранения при обычном входе не нужны. Матч начнётся только после загрузки: «PRIME CLOUD · Синхронизация…».
- **Сохраняется само.** После матча изменения уходят на сервер примерно через секунду, остальные — через несколько секунд. «Синхронизировано» показывается только после ответа сервера.
- **Старая вкладка ничего не испортит.** Сервер проверяет каждую запись: она должна прийти от действующей сессии. Запрос вкладки, потерявшей управление, отклоняется, даже если пришёл позже. Матч, который закончился уже после потери управления, наград не даёт.
- **Нет связи дольше ~75 секунд** — новые матчи под PRIME ID не начинаются. Можно повторить или играть как гость. Неотправленное ждёт на устройстве. Если за это время на другом устройстве уже играли, эта версия не смешивается с облаком, а сохраняется в «Облачных копиях».
- В этом же обновлении на сервер приезжает ручное подтверждение без почты из 1.8.2: сервер перестаёт пытаться отправлять письма.

Не меняются:

- приглашения и `invite_only`;
- ручное подтверждение email;
- пароли, аккаунты и сохранения;
- экономика, бои, гостевой режим;
- схема сохранения (v12).

Подробности — в отчёте и в [SAVE_AND_PRIME_ID.md](SAVE_AND_PRIME_ID.md), раздел 11.

## 2. Порядок (коротко)

1. Проверки на Mac.
2. Свежая резервная копия сервера, скачанная на Mac.
3. *(рекомендуется)* Проверка миграции на копии серверной базы на Mac.
4. **Сначала сайт.** Новый клиент работает и со старым сервером, по правилам 1.8.2.
5. **Потом сервер**, в спокойное время.
6. Проверки сервера.
7. Тестировщики обновляют страницу.
8. Ручная проверка на устройствах.

Почему сначала сайт: новая игра узнаёт у сервера, включены ли сессии, и со старым сервером ведёт себя как 1.8.2. А вот старая игра (1.8.2) после обновления сервера сохранять в облако не сможет: сервер требует сессию. Её прогресс не теряется, он ждёт на устройстве до обновления страницы. Поэтому промежуток между шагами 4 и 5 лучше делать коротким, а не наоборот.

## Шаг 0. Проверки на Mac

```bash
npm run build && npm run accounts && npm run backend:test && npm run beta:test && npm run cloud:test
```

Должно быть:

- `accounts: OK`;
- `backend: OK` — правила 1.8.2 через выключатель `PRIME_SESSIONS=off`;
- `beta: OK`;
- `cloud: OK` — сессии PRIME CLOUD 2.0.

Тесты запускают свой временный PocketBase и удаляют его. Ни вашу локальную базу, ни сервер они не трогают. Если открыт SSH-туннель на порту 18090, это не мешает: проверки этот порт не используют. Если какой-то их порт занят, они откажутся запускаться и ничего никуда не отправят.

## Шаг 1. Резервная копия сервера

```bash
$ sudo systemctl start prime-backup
$ sudo journalctl -u prime-backup -n 5 --no-pager
$ sudo ls -lt /var/backups/primetime | head -3
```

В журнале должно быть `OK: …tar.gz (аккаунтов N, сохранений M)`. Скачайте этот архив на Mac:

```bash
mkdir -p ~/Documents/prime-server-backups
scp root@IP-СЕРВЕРА:/var/backups/primetime/pb_data-ИМЯ.tar.gz ~/Documents/prime-server-backups/
```

Ключ `PB_ENCRYPTION_KEY` у вас уже сохранён отдельно. Без него копия бесполезна.

## Шаг 2. *(рекомендуется)* Миграция на копии настоящей базы

Проверка запускает новую миграцию на **временной копии** скачанного архива и сравнивает аккаунты, хеши паролей, никнеймы, сохранения, историю и приглашения до и после. Сам архив только читается, копия удаляется. Настройки серверной базы зашифрованы, поэтому нужен ключ. Его вводят так, чтобы он не попал ни в историю команд, ни в файлы:

```bash
read -rs PB_ENCRYPTION_KEY
```

Вставьте ключ и нажмите Enter. На экране ничего не появится — так и должно быть.

```bash
export PB_ENCRYPTION_KEY
```

```bash
npm run backend:migrate-check -- ~/Documents/prime-server-backups/pb_data-ИМЯ.tar.gz
```

```bash
unset PB_ENCRYPTION_KEY
```

Ожидаемый ответ:

```
Миграции PRIME на копии: …, 1792500000_prime_sessions.js
Коллекция invites: есть · game_sessions (1.8.3): есть
OK: аккаунты, хеши паролей, статусы email, никнеймы, сохранения, ревизии и история не изменились.
```

Если вместо `OK` написано `ОШИБКА` — **сервер не обновлять**, пришлите вывод.

## Шаг 3. Сайт

Как в [PRIME_BETA_PUBLISH.md](PRIME_BETA_PUBLISH.md), шаги 2–6:

```bash
git -C ~/Desktop/"PRIME TIME SHOWDOWN" tag before-1.8.3
```

```bash
npm run publish:sync -- ~/Desktop/"PRIME TIME SHOWDOWN"
```

```bash
npm run publish:sync -- ~/Desktop/"PRIME TIME SHOWDOWN" --apply
```

Затем VS Code → Source Control. Проверьте, что в списке нет `pb_data`, `bin`, `backups`, `backups-private`, `server-bundle`, `.db` и `.zip`. Сделайте один коммит «Alpha 1.8.3 PRIME CLOUD 2.0» и Sync.

Проверка:

- GitHub → Actions — сборка зелёная.
- На сайте внизу заставки **ALPHA 1.8.3 · PRIME CLOUD 2.0**.
- Сервер ещё старый, поэтому PRIME ID работает как в 1.8.2: вход и синхронизация, в меню строка «PRIME CLOUD · СИНХРОНИЗИРОВАНО». Строки «играть сейчас можно только здесь» ещё нет — это правильно.

## Шаг 4. Сервер

На Mac:

```bash
npm run server:bundle
```

```bash
scp server-bundle/prime-server-1.8.3-alpha.tar.gz* root@IP-СЕРВЕРА:/root/
```

На сервере:

```bash
$ cd /root && sha256sum -c prime-server-1.8.3-alpha.tar.gz.sha256
$ rm -rf prime-1.8.3 && mkdir prime-1.8.3 && tar -xzf prime-server-1.8.3-alpha.tar.gz -C prime-1.8.3
$ cd prime-1.8.3 && sudo bash deploy/linux/update.sh
```

Что делает `update.sh`:

1. Делает свежую копию базы.
2. Заменяет код, сохраняя прежний как `*.previous`.
3. Перезапускает PocketBase. Миграция 1.8.3 применяется при запуске.
4. Ждёт ответа. Ожидаемый вывод: `OK: обновлено`.

Если `update.sh` сообщил ошибку, он сам вернул прежний код. Смотрите шаг 8.

Настройки в `/etc/primetime/pocketbase.env` менять **не нужно**.

## Шаг 5. Проверки сервера

```bash
$ sudo /opt/primetime/deploy/healthcheck.sh primetime-showdown-beta.duckdns.org
```

Всё `OK`, в том числе строка «PRIME CLOUD 2.0: одна активная игровая сессия на PRIME ID включена».

```bash
curl -s https://primetime-showdown-beta.duckdns.org/api/prime/config
```

В ответе должны быть `"sessions":1` и `"mail":false`.

```bash
$ sudo sqlite3 /var/lib/primetime/pb_data/data.db "select file from _migrations where file like '%prime%';"
```

В списке должен быть `1792500000_prime_sessions.js`.

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://primetime-showdown-beta.duckdns.org/api/collections/game_sessions/records
```

Ответ `403`: сессии недоступны через обычный API.

В панели (через туннель) появилась коллекция `game_sessions`. Строки появятся, когда кто-то откроет игру. Ключей там нет, только их хеши.

## Шаг 6. Тестировщикам

«Обновите страницу игры (или закройте вкладку и откройте снова)».

Пока страница старая:

- новая игра, открытая до обновления сервера, покажет «Обновите страницу, чтобы продолжить синхронизацию»;
- старая 1.8.2 покажет «Сервер не принял сохранение».

Прогресс при этом остаётся на устройстве. После обновления страницы он отправится сам, а если тот же аккаунт уже играл на другом устройстве, сохранится в «Облачных копиях».

## Шаг 8. Если что-то пошло не так

| Признак | Что делать |
|---|---|
| `update.sh` написал «PocketBase не ответил» | Код уже возвращён прежний. Журнал: `sudo journalctl -u pocketbase -n 80 --no-pager`. Базу восстанавливать только если журнал говорит об ошибке миграции — командой, которую напечатал `update.sh` |
| Игра везде пишет «нет соединения», а `curl …/api/health` работает | Проверьте `PRIME_ORIGINS` и что сайт обновился (подпись 1.8.3) |
| Постоянно «PRIME ID открыт на другом устройстве», хотя открыто одно устройство | Закройте лишние вкладки и нажмите «Продолжить здесь». Если повторяется — сразу аварийный выключатель (ниже) и пришлите описание |
| Нужно срочно вернуть поведение 1.8.2 без отката кода | Аварийный выключатель, ниже |

**Аварийный выключатель.** Ничего в базе не меняет, сохранения снова принимаются по правилам 1.8.2:

```bash
$ sudo nano /etc/primetime/pocketbase.env
$ sudo systemctl restart pocketbase
```

В файле поставьте `PRIME_SESSIONS=off`. Новая игра после обновления страницы сама перейдёт на правила 1.8.2. Включить обратно: удалите `off` и снова перезапустите.

## Шаг 9. Откат

Возврат только сайта **не отменяет** изменений сервера: таблица сессий и проверка сессий остаются. Поэтому порядок такой.

- **Откатить сайт:**

  ```bash
  git -C ~/Desktop/"PRIME TIME SHOWDOWN" revert --no-edit HEAD
  ```

  Затем Sync. Если сервер уже на 1.8.3, **обязательно** включите аварийный выключатель (`PRIME_SESSIONS=off`), иначе старая игра не сможет сохранять в облако.
- **Откатить код сервера.** `update.sh` хранит прежний код рядом:

  ```bash
  $ sudo systemctl stop pocketbase
  $ for d in pb_hooks pb_migrations pb_public; do sudo rm -rf /opt/primetime/$d && sudo mv /opt/primetime/$d.previous /opt/primetime/$d; done
  $ sudo systemctl start pocketbase
  ```

  Прежний код запускается на уже обновлённой базе: это проверено. Лишняя таблица `game_sessions` ему не мешает и данные не затрагивает.
- **Восстановить базу** — только при повреждении данных. Используйте `restore.sh` с копией из шага 1 или из `update.sh` ([PRIME_CLOUD_BACKUP.md](PRIME_CLOUD_BACKUP.md)). Всё, что игроки сохранили после копии, пропадёт из облака, поэтому это крайняя мера.

Миграция 1.8.3 только **добавляет** таблицу. Аккаунты, сохранения, история и приглашения не меняются (шаг 2 это показывает на вашей настоящей базе).
