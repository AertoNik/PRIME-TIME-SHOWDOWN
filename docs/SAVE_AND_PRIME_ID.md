# Сохранения и PRIME ID (Alpha 1.8 · аккаунты — Alpha 1.8.1 · закрытая бета — Alpha 1.8.2 Stage 1)

## 1. Где лежит прогресс

Всё хранится локально в `localStorage` браузера; сетевых запросов нет. Ключи одного профиля — `profileKeys(profile)` в `src/meta/SaveSystem.ts`:

| Ключ | Что внутри |
|---|---|
| `primetime-showdown-save-v1` | само сохранение (`SaveData`, поле `version` — схема) |
| `…:backups` | до 3 резервных копий: `{ at, reason, app, summary, raw }`, `raw` — текст сохранения как он был |
| `…:damaged` | отложенное нечитаемое сохранение `{ at, app, raw }` |
| `…:meta` | метаданные записи: `{ revision, savedAt, app, device }` (не внутри сохранения) |
| `…:lock` | какая вкладка сейчас владеет профилем: `{ id, at }` |
| `primetime-showdown-device-v1` | случайный id этого браузера (для экспорта и будущей синхронизации; не отпечаток устройства) |

Гость (`'guest'`) использует исторический ключ, поэтому все старые карьеры загружаются как раньше. Будущий аккаунт (`'user:<id>'`) получит свои ключи `primetime-showdown-save-v1:user:<id>…` — гостевое сохранение при этом не трогается.

## 2. Схема и миграции

`VERSION = 12`. Любое изменение данных обязано поднять схему. `sanitize()` накладывает прочитанное на `defaultSave()` и чинит каждое поле, поэтому любая старая схема (1–11) читается без отдельных шагов миграции; недостающее получает значения по умолчанию. Отсутствующее поле `version` = схема 1.

v12 добавила:

- `streak: { current, best, since }` — серия побед продюсера; `since` — с какого момента ведётся учёт (у старых сохранений — первый запуск 1.8);
- `fighters.<id>.streak` и `fighters.<id>.bestStreak` — личные серии.

Неизвестные верхнеуровневые поля сохраняются в `extra` и записываются обратно (`{ ...extra, ...data, version }`), поэтому поля более новой версии не теряются.

## 3. Статусы при запуске

`SaveSystem.status`:

- `ok` — прочитано (или сохранения ещё нет);
- `unavailable` — браузер не даёт хранилище (приватный режим, запрет): игра идёт без сохранения;
- `damaged` — текст не читается как сохранение. Он копируется в `…:damaged`, основной ключ **не перезаписывается**, пока игрок не выберет: восстановить копию (`restoreBackup`) или начать заново (`startFresh`). Окно — `showDamaged` в `src/ui/saveCare.ts`;
- `newer` — схема выше, чем знает эта версия. Данные показываются, но ничего не пишется (`writable === false`); окно предлагает обновить страницу, скачать копию или играть без сохранения.

`writable` = не `damaged`, не `newer` и вкладка не пассивная. `save()` и `reset()` проверяют его сами, так что вызывающему коду не нужно помнить об этом.

## 4. Резервные копии

`MAX_BACKUPS = 3`, новые сверху, копия без прогресса не создаётся, одинаковая с последней — тоже. Когда:

- `migration` — при запуске, если схема сохранения старше текущей (до первой записи в новой схеме);
- `auto` — при запуске, если последней копии больше 20 часов;
- `reset`, `import`, `restore` — перед тем как текущее сохранение будет заменено.

Восстановление и импорт сохраняют настройки этого устройства (звук, музыку, качество, камеру) — кроме восстановления после повреждения: там текущие настройки лишь значения по умолчанию, поэтому возвращаются настройки из копии. После замены страница перезагружается, чтобы все системы прочитали новое состояние с нуля.

## 5. Экспорт и импорт

`exportJSON()` выдаёт конверт:

```json
{ "format": "primetime-showdown-save", "exportedAt": "…", "app": "1.8-alpha", "schema": 12,
  "profile": "guest", "status": "ok", "meta": { … }, "save": { …сохранение как оно хранится… } }
```

(при повреждении — ещё поле `damaged` с исходным текстом). `checkImport(text)` ничего не меняет: принимает конверт или голое сохранение, отклоняет файлы больше 512 КБ, не-JSON, JSON без `fighters` и `money` и сохранения более новой схемы; возвращает сводку для окна подтверждения. `applyImport(check)` заменяет прогресс только после подтверждения игрока.

## 6. Две вкладки

`TabLock` (`src/meta/TabLock.ts`): вкладка-владелец обновляет `…:lock` раз в 2 с; запись старше 8 с считается брошенной (вкладка закрылась или упала). Вторая вкладка открывается пассивной (`passive`) и ничего не пишет. «Играть здесь» — `takeOver()`: профиль переходит к этой вкладке, первая узнаёт об этом из события `storage` (и перед каждой записью проверяет `lock.owns()`), сразу перестаёт писать и показывает окно. `pagehide` освобождает профиль, `pageshow` из кэша возвращает его.

Ограничение: если браузер закрывает вкладку без `pagehide`, профиль освобождается через 8 с — «Играть здесь» работает и раньше.

## 7. Серии побед

Единственная точка — `CareerSystem.applyMatch` (вызывается один раз за бой из `Game.finishMatch`, защищено флагом `resultsShown`; обучение и Survival выходят раньше). Победа: `current++`, `best = max(best, current)` — у продюсера и у бойца матча. Поражение, ничья, сдача: `current = 0`. Рекорд не уменьшается никогда. Волны Survival в карьерные матчи не входят — у марафона свои рекорды (`modes.survival`). Prime Challenge и Boss Fight — карьерные матчи и считаются.

## 8. PRIME ID

- `src/meta/ProducerProfile.ts` — чистые функции поверх сохранения: `buildProfile`, `hallOfFame`, `favouriteOf`, `mostWinsOf`, `bestStreakOf`, `winRate` (`null` до первого матча — без NaN). Ничего не хранят и не пишут. Видимость бойцов — `EventManager.fighterVisible` (Люсьен — после покупки или во время события).
- `src/ui/screens/ProfileScreen.ts` — экран: карточка-пропуск и вкладки «Обзор / Зал славы / Коллекция». Открывается бейджем уровня в главном меню.
- Статус профиля сейчас один — `'guest'`. Тип `ProfileStatus` расширяется в 1.8.1; экран не должен показывать синхронизацию, которой нет.

## 9. Аккаунты и облачные сохранения (Alpha 1.8.1, локальный тест)

Подробная инструкция запуска — [`docs/ACCOUNTS_LOCAL.md`](ACCOUNTS_LOCAL.md). Архитектура:

```
игра → SaveSystem (локально, синхронно, работает офлайн) → SyncManager → PocketBase (127.0.0.1:8090)
```

- **Профили.** Гость — исторический ключ; аккаунт — свой слот `primetime-showdown-save-v1:user:<id>` (`profileKeys`). Какой профиль играет браузер — `primetime-showdown-accounts-v1` (`src/net/accountStore.ts`); страница запускается на аккаунте, только если его локальная копия уже записана (`bootProfile`). Переключение = запись слота заранее + `SaveSystem.suspend()` + перезагрузка.
- **Копия для облака** (`src/net/cloudSave.ts`): тот же SaveData без `settings`, канонический JSON (ключи отсортированы) и его SHA-256 (`src/net/sha256.ts`, тот же хеш считает сервер). Схема сохранения не менялась — v12.
- **Метаданные синхронизации** — отдельно от прогресса, `<ключ профиля>:sync`: подтверждённая сервером ревизия и хеш, неподтверждённая запись (`pending` с id запроса), открытый конфликт, «новая схема в облаке».
- **SyncManager** (`src/net/SyncManager.ts`): после каждой локальной записи (`SaveSystem.onSaved`) отмечает изменения и отправляет их через ~20 с, после матча — через ~3 с, по одному запросу, с паузами 5–60 с при ошибках сети; при уходе со страницы пробует отправить (keepalive), но на это не полагается. «Синхронизировано» — только после ответа сервера. Решения по конфликтам — чистая функция `decideSync`.
- **Сервер** (`backend/pb_hooks`): единственный путь записи — `PUT /api/prime/save` (владелец = вошедший пользователь, подтверждённый email, проверка размера/хеша/данных, ревизия + копия в историю + запись в одной транзакции, идемпотентность по `op`), `POST /api/prime/save/archive`, `POST /api/prime/save/restore`. Чтение — обычный API PocketBase, правила коллекций пускают только владельца.
- **AccountService** (`src/net/AccountService.ts`): что происходит после входа (`planFor`), перенос гостевой карьеры, новая карьера, выход. **AccountRuntime** (`src/game/AccountRuntime.ts`) и **accountUI** (`src/ui/accountUI.ts`) попадают в сборку только в `npm run dev:accounts` или при `VITE_PRIME_ACCOUNTS=beta|production` (1.8.2); обычный `npm run build` их не содержит.

## 10. Закрытая бета (Alpha 1.8.2 Stage 1)

Подробно — [`PRIME_CLOUD_PREDEPLOY.md`](PRIME_CLOUD_PREDEPLOY.md). Для сохранений важно:

- **Схема сохранения не менялась (v12)**, формат облачной копии и метаданных синхронизации — тоже. Миграция сервера 1.8.2 только добавляет коллекцию `invites`; аккаунты, сохранения, ревизии и история на копии реальной локальной базы не изменились (`npm run backend:migrate-check`).
- **Окружения** (`src/net/config.ts`, `src/net/build.ts`): `local` (Mac, только loopback), `beta` и `production` (только `https://`, адрес из `VITE_PRIME_API_URL`). Режим регистрации игра не задаёт — она читает его с сервера (`GET /api/prime/config`) и при отсутствии ответа считает регистрацию закрытой.
- **SyncManager в условиях настоящего интернета** проверен в `npm run beta:test`: ответ медленнее таймаута (запрос повторяется, сервер узнаёт его по `op` — одна ревизия), ошибка 503 (повтор, «Синхронизировано» только после успеха), сессия завершена на сервере («войдите снова», изменение остаётся на устройстве и уходит после входа), обрыв связи сразу после матча с перезагрузкой страницы (результат сохранён и отправлен после запуска). Таймаут запросов к удалённому серверу — 15 с (локальному — 10 с).
- **Удаление аккаунта** (по просьбе тестировщика, через панель администратора) удаляет профиль, облачное сохранение и историю; гостевая карьера в браузере не трогается.

## 11. Проверки

`npm run primeid` — 80 проверок на искусственных образцах формата 1.7.6 и старых схем (не на файлах реальных игроков): перенос, серии, отсутствие двойного счёта, повреждение, копии, экспорт/импорт, новая схема, две вкладки, недоступное хранилище, настройки устройства, цифры PRIME ID и то, что просмотр профиля ничего не пишет.

`npm run accounts` — 72 проверки слоя аккаунтов, закрытой беты, обеих сборок (обычная — без аккаунтов, beta — с сервером) и набора для VPS без сервера. `npm run backend:test` — 97 проверок на настоящем PocketBase и Mailpit с временной базой (регистрация, письма, перенос, синхронизация, конфликты, повтор запроса, падение сервера, права доступа, лимиты, копия базы). `npm run beta:test` — 53 проверки закрытой беты на настоящем PocketBase (приглашения, режимы, обход через API, ручное подтверждение без почты, плохое соединение, копии, перенос базы, удаление аккаунта).
