# PRIME CLOUD — резервные копии и восстановление

Главное правило: **копия, которую ни разу не пробовали восстановить, — не копия.** И она должна лежать не только там же, где сама база.

---

## 1. На Mac (локальный тест)

### Копия, сделанная перед Alpha 1.8.2

```
backups-private/pb_data-2026-10-18_221817-before-1.8.2/      data.db, auxiliary.db, SHA256SUMS
backups-private/pb_data-2026-10-18_221817-before-1.8.2.zip   то же одним архивом
```

- Сделана при **остановленном** backend, поэтому копия согласованная.
- Целостность проверена (`PRAGMA integrity_check`), контрольные суммы совпадают с исходной базой.
- Восстановление проверено на отдельной копии.
- Исходная `backend/pb_data` не удалялась.

Папка `backups-private/` в git не попадает: это прописано в `.gitignore`, и внутри лежит свой `.gitignore` с `*`. **Не копируйте её в папку GitHub-репозитория.** Хорошая идея — положить `.zip` ещё и на внешний диск или флешку.

Проверить, что копия не испортилась:

```bash
cd ~/Desktop/"PRIME TIME Duel"/backups-private/pb_data-2026-10-18_221817-before-1.8.2
shasum -a 256 -c SHA256SUMS
```

Оба файла должны быть `OK`.

### Новая копия

```bash
npm run backend:backup
```

С 1.8.2 команда работает **и при запущенном backend**: она использует встроенное онлайн-копирование SQLite, а не простое копирование файла. Результат:

- `backend/backups/pb_data-ДАТА/` и `.zip`;
- в выводе — сколько внутри аккаунтов, сохранений и приглашений.

Другая папка для копии: `npm run backend:backup -- --out ~/Documents/prime-backups`.

### Проверить новую версию на копии, а не на рабочей базе

```bash
npm run backend:migrate-check -- backups-private/pb_data-2026-10-18_221817-before-1.8.2
```

Что делает команда:

1. Копирует резервную копию во временную папку.
2. Запускает на ней текущие миграции. Регистрация при этом закрыта, порт 18290.
3. Сравнивает аккаунты, хеши паролей, статусы email, никнеймы, сохранения, ревизии и историю.
4. Удаляет временную папку.

Сама резервная копия только читается. Ответ `OK: … не изменились` означает, что миграции безопасны для этих данных. Запускайте эту проверку перед каждой новой миграцией.

### Восстановить локальную базу из копии

1. Остановите backend: `npm run backend:stop` или Ctrl+C в его вкладке.
2. Отложите текущую базу. Не удаляйте её:

   ```bash
   mv backend/pb_data backend/pb_data-before-restore-$(date +%Y%m%d-%H%M%S)
   mkdir backend/pb_data
   ```

3. Положите файлы из копии. Пример для копии перед 1.8.2:

   ```bash
   cp backups-private/pb_data-2026-10-18_221817-before-1.8.2/data.db backups-private/pb_data-2026-10-18_221817-before-1.8.2/auxiliary.db backend/pb_data/
   ```

   Для `.zip`: распакуйте двойным щелчком и скопируйте `data.db` и `auxiliary.db` из распакованной папки.
4. Запустите `npm run backend`. Если копия старше 1.8.2, миграция 1.8.2 применится снова. Это проверено командой `migrate-check`.

## 2. На сервере (после Stage 2)

### Что делается само

Служба `prime-backup.timer` каждый день примерно в 03:30 UTC запускает `/opt/primetime/deploy/backup.sh`. Если сервер в это время был выключен, копия делается после включения. Скрипт:

1. Копирует `data.db` встроенным онлайн-копированием SQLite. PocketBase при этом продолжает работать. С 1.8.4 `auxiliary.db` (журнал запросов с IP-адресами, хранится 7 дней) в копии не попадает: после восстановления PocketBase начинает журнал заново.
2. Копирует загруженные файлы (`storage/`), если они есть.
3. Проверяет каждую копию через `PRAGMA integrity_check`.
4. Записывает контрольные суммы `SHA256SUMS`, счётчики `COUNTS` и время `CREATED_UTC`.
5. Упаковывает всё в `/var/backups/primetime/pb_data-ДАТА-ВРЕМЯ-N.tar.gz`.
6. Оставляет 14 последних архивов. Число меняется настройкой `PRIME_BACKUP_KEEP`.

| Действие | Команда |
|---|---|
| сделать копию сейчас | `sudo systemctl start prime-backup` |
| результат | `sudo journalctl -u prime-backup -n 20 --no-pager` |
| список копий | `sudo ls -lt /var/backups/primetime` |
| когда следующая | `systemctl list-timers prime-backup.timer` |

`update.sh` сам делает копию перед каждым обновлением.

Дополнительные настройки копий лежат в необязательном файле `/etc/primetime/backup.env`, по одной строке `КЛЮЧ=значение`:

```
PRIME_BACKUP_KEEP=14
PRIME_BACKUP_AGE_RECIPIENT=
PRIME_BACKUP_UPLOAD_CMD=
```

### Восстановление на сервере

```bash
sudo /opt/primetime/deploy/restore.sh /var/backups/primetime/pb_data-20261101-033012-1234.tar.gz
```

Что делает `restore.sh`:

1. Проверяет архив: контрольные суммы и целостность SQLite.
2. Показывает, сколько в копии аккаунтов и сохранений, и спрашивает подтверждение `y`.
3. Останавливает PocketBase.
4. Переносит **текущие** данные в `/var/lib/primetime/pb_data.before-restore-ДАТА`. Они не удаляются.
5. Кладёт копию на место, запускает PocketBase и ждёт ответа.

Если что-то не так, прежние данные лежат в папке `.before-restore-…`.

**Пробное восстановление без остановки сервера.** Раз в месяц полезно проверить, что копия читается:

```bash
sudo PRIME_DATA_DIR=/tmp/restore-test PRIME_RESTORE_SKIP_SERVICE=1 /opt/primetime/deploy/restore.sh /var/backups/primetime/pb_data-….tar.gz
sudo rm -rf /tmp/restore-test
```

Работающий сервер и его данные при этом не затрагиваются.

### Ключ шифрования — без него копия бесполезна

PocketBase хранит свои настройки, включая пароль SMTP, зашифрованными ключом `PB_ENCRYPTION_KEY` из `/etc/primetime/pocketbase.env`. Проверено (`npm run beta:test`, раздел «Перенос базы»):

- с тем же ключом копия запускается на другом сервере, аккаунты входят;
- **с другим ключом PocketBase не запускается** (`cipher: message authentication failed`). Данные при этом не портятся, но без прежнего ключа сервер с этой базой не поднять.

Поэтому **копия `/etc/primetime/pocketbase.env` хранится вместе с копиями базы**, в личном менеджере паролей или заметках, но не в git. Если `restore.sh` упал из-за ключа, он сам об этом скажет.

## 3. Копии вне сервера (зашифрованные)

Если VPS удалят, взломают или провайдер потеряет диск, копии в `/var/backups/primetime` пропадут вместе с ним. Нужна хотя бы одна копия **в другом месте**. Платные хранилища не подключены — выбор за вами (см. чек-лист).

### Бесплатный вариант: забирать копию на Mac

Раз в неделю и перед любыми рискованными действиями. На Mac:

```bash
ssh root@203.0.113.10 'ls -1t /var/backups/primetime | head -3'
scp root@203.0.113.10:/var/backups/primetime/pb_data-ИМЯ.tar.gz ~/Documents/prime-server-backups/
```

На Mac копию можно проверить и даже поднять локально:

1. Распакуйте архив.
2. Выполните `shasum -a 256 -c SHA256SUMS` в его папке.
3. Запустите `npm run backend:migrate-check -- <папка>`.

Перед `scp` создайте папку `~/Documents/prime-server-backups` и держите её вне папки проекта.

### Шифрование для внешнего хранилища (age)

Скрипт уже умеет делать **дополнительную зашифрованную копию** `.tar.gz.age` для отправки наружу. Копия на самом сервере остаётся читаемой: она нужна для быстрого отката после неудачного обновления.

1. На **Mac** поставьте `age`, например `brew install age`, и создайте пару ключей:

   ```bash
   age-keygen -o ~/prime-backup-age-key.txt
   ```

   Команда напечатает открытый ключ `age1…`. Файл `prime-backup-age-key.txt` — **закрытый ключ**:
   - не кладите его на сервер, в проект или в git;
   - сделайте ему копию, например на флешку;
   - без него зашифрованные копии не открыть.
2. На **сервере** впишите открытый ключ в `/etc/primetime/backup.env`:

   ```
   PRIME_BACKUP_AGE_RECIPIENT=age1…
   ```

3. Когда будет выбрано хранилище, впишите команду выгрузки в `PRIME_BACKUP_UPLOAD_CMD`. Ей передаётся путь к **зашифрованной** копии как `$1`. Без ключа `age` скрипт ничего наружу не отправит.

Восстановление из зашифрованной копии: положите закрытый ключ на сервер **временно**, затем выполните:

```bash
sudo PRIME_AGE_IDENTITY=/root/prime-backup-age-key.txt /opt/primetime/deploy/restore.sh /путь/pb_data-….tar.gz.age
sudo rm /root/prime-backup-age-key.txt
```

Ветки шифрования и выгрузки проверены на Mac с заглушкой вместо `age`. Настоящий `age` на Mac не установлен и не запускался.

## 4. Перенос базы на другой сервер

1. На старом сервере: `sudo systemctl start prime-backup`, затем заберите архив на Mac (`scp`).
2. Сохраните старый `/etc/primetime/pocketbase.env`.
3. На новом сервере **до** `install.sh` положите старый файл настроек, чтобы не создался новый ключ:

   ```bash
   sudo mkdir -p /etc/primetime
   sudo nano /etc/primetime/pocketbase.env      # вставить содержимое старого файла
   ```

   Затем `install.sh` (см. [PRIME_CLOUD_DEPLOY.md](PRIME_CLOUD_DEPLOY.md)). Он увидит файл и не станет его менять.
4. Загрузите архив на новый сервер и выполните `restore.sh` с ним.
5. Если поменялся IP, обновите DNS-запись `api`. Игру пересобирать не нужно: она обращается к домену, а не к IP.
6. Выполните `healthcheck.sh`, войдите своим аккаунтом и только потом удаляйте старый сервер.

Этот перенос проверен на Mac в `npm run beta:test`: `backup.sh` → `restore.sh` → запуск с тем же ключом → вход. На настоящих VPS он не выполнялся.

## 5. Что сохранить перед удалением VPS

- [ ] свежий архив базы (`prime-backup`) — скачан на Mac и проверен `shasum -c`;
- [ ] `/etc/primetime/pocketbase.env` — с `PB_ENCRYPTION_KEY`, данными SMTP и режимом регистрации;
- [ ] `/etc/primetime/backup.env`, если создавали;
- [ ] `/etc/caddy/Caddyfile`, если меняли вручную (иначе он восстанавливается из проекта);
- [ ] закрытый ключ `age`, если включали шифрование (он и так должен быть только у вас);
- [ ] список приглашений: `sudo /opt/primetime/deploy/invites.sh list all` (сами коды не восстановить — только их статус);
- [ ] email и пароль суперпользователя (в менеджере паролей).

Пока всё это не на Mac и не проверено, сервер не удалять.
