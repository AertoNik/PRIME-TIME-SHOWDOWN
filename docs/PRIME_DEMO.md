# Демонстрационная оплата на официальном сайте (PRIME_PAY_MODE=demo) — Alpha 1.8.8

> **Статус (23.10.2026): реализовано и проверено локально (`npm run payments` — 237 проверок, из них разделы «Демонстрация…» и «Одни адреса Robokassa…»; путь игрока пройден в браузере на локальной песочнице `npm run payments:sandbox -- --demo`). НЕ включено ни на одном сервере. С настоящей тестовой страницей Robokassa демо-режим ещё не проверялся — сначала репетиция на staging (раздел 6).**

## 1. Что получает модератор Robokassa (и любой подтверждённый PRIME ID)

1. https://primetimeshowdown.online → вход в PRIME ID (регистрация по приглашениям сохраняется; подходит любой существующий аккаунт с подтверждённым email и принятыми документами).
2. PRIME SHOP: настоящие цены (RAY 99 ₽, BRUNO 149 ₽, эффекты по 49 ₽), значок «ДЕМО-ОПЛАТА», строка «Демо-оплата · деньги не списываются».
3. Окно PRIME CHECKOUT: полоса **«ТЕСТОВАЯ ПОКУПКА — НАСТОЯЩИЕ ДЕНЬГИ НЕ СПИСЫВАЮТСЯ»**, «Цена товара 99 ₽» и «Тестовая оплата 99 ₽ · деньги не списываются», отметка «Я понимаю, что это демонстрационная оплата Robokassa…».
4. Официальная страница Robokassa в **тестовом режиме** (`IsTest=1`, подпись тестовым Паролем #1) — сумма = настоящая цена; денег не списывается.
5. Автоматический возврат на официальный сайт → «ТЕСТОВАЯ ПОКУПКА ПОДТВЕРЖДЕНА · ДОБРО ПОЖАЛОВАТЬ В PRIME COLLECTION» — только после подтверждения сервером (ResultURL с тестовым Паролем #2).
6. Предмет в «Моей коллекции» с пометкой «Тестовая покупка»; его можно надеть.

## 2. Выбранная архитектура и почему

**Третий, отдельный режим `demo` на production-сервере** (`backend/pb_hooks/lib/payments.js`). Тестовый режим на production по-прежнему запрещён (`test_on_production`) — демонстрация это не «ослабленное условие», а отдельное окружение со своими правилами:

| Свойство | Как обеспечено |
|---|---|
| Только тестовая страница Robokassa | В режиме demo сервер берёт **только** тестовые пароли и всегда ставит `IsTest=1`. Есть хоть один боевой пароль → оплаты нет (`live_secrets_on_demo_server`). Тестовой подписью нельзя провести боевой платёж. |
| Никаких настоящих списаний | Следствие предыдущей строки: в тестовом режиме Robokassa денег не списывает; боевых паролей на сервере нет. |
| Отдельные заказы, права, журнал счетов | Окружение `demo`: свои заказы и права (`env = demo`), свой журнал `prime-ledger/demo`, свой диапазон счетов **от 700 000 000 000 000** (staging — от 5·10¹⁴, боевые — от 10¹⁰). |
| Тестовые права не попадут в настоящий магазин | Демо-права учитываются, только пока демонстрация работает. Боевой режим учитывает только `live`. Команда `prime-shop demo-end` отзывает все демо-права (история сохраняется). |
| Не бесконечно | `PRIME_DEMO_UNTIL` обязателен: последний день по Москве, не дальше 92 дней. После него оплата выключается сама, а демо-права перестают учитываться. |
| Только косметика | Персонаж (LUCIEN) в демонстрации не продаётся никогда (`not_in_demo`), даже если его цену когда-то утвердят. |
| Браузер ничего не переключит | Режим — настройка сервера (`/etc/primetime/pocketbase.env`). Браузер присылает только `sku`. |
| Поддельные уведомления | Та же проверка ResultURL: подпись тестовым Паролем #2, сумма, `Shp_order`, окружение заказа. `IsTest=0` отклоняется. Возврат на сайт (SuccessURL) ничего не выдаёт. |
| Базы не смешиваются | Демонстрация идёт в базе production, с её аккаунтами. Staging и его база не участвуют. Ничего не копируется. |

**Рассмотренные варианты:**
- *Отдельный демонстрационный сервер (staging или новый) с «мостом» входа* (production выдаёт подписанный короткий билет, демо-сервер его проверяет). Production не хранил бы даже тестовых паролей — но нужны общий ключ подписи на двух серверах, второй адрес API в игре, CORS, отдельная выдача прав, а на staging попадали бы идентификаторы и никнеймы настоящих игроков (персональные данные на тестовом сервере). Сложнее в сопровождении и хуже для данных → отклонён.
- *Перенос аккаунтов в staging* — запрещён заданием (нельзя смешивать базы) → отклонён.
- *ResultUrl2 Robokassa* как отдельный канал уведомлений: это **дополнительное** уведомление в формате JWS (подпись RSA). PocketBase не умеет проверять RSA, а без проверки уведомление подделывается → нельзя считать доказательством оплаты (docs.robokassa.ru/ru/notifications-and-redirects) → не используется.

**Цена демонстрации.** Сумма тестового платежа = утверждённая цена (99 ₽ и т. д.): в тестовом режиме деньги не двигаются, и модератор видит одну и ту же сумму в каталоге, в окне и на странице Robokassa. На staging по-прежнему тестовые 10 ₽ — рядом с ценой товара пишется «Тестовая оплата 10 ₽ · деньги не списываются».

**Что это значит для игроков.** Любой подтверждённый PRIME ID во время демонстрации может «купить» косметику тестовой оплатой. Такие предметы отмечены «Тестовая покупка», не являются покупкой и исчезают, когда демонстрация заканчивается (или начинаются настоящие продажи). Это прямое следствие решения «демо для всех подтверждённых аккаунтов» — его стоит учитывать при выборе длительности.

## 3. Один магазин Robokassa — одни адреса ResultURL / SuccessURL / FailURL

В кабинете у магазина один набор адресов (отдельных адресов для тестового режима нет). Решение:

1. Адреса в кабинете указывают на **production**: `https://api.primetimeshowdown.online/api/prime/pay/robokassa/{result,success,fail}` (Result — POST).
2. Production с `PRIME_PAY_RELAY_URL=http://127.0.0.1:8091` (staging на том же VPS) **передаёт** уведомления и возвраты по счетам **тестового диапазона** (staging) на staging без изменений и отвечает Robokassa ответом staging. Сам production по ним ничего не проверяет, не записывает и не выдаёт. Работает и при выключенной оплате на production.
   **Возврат игрока (Alpha 1.8.9):** по тестовому счёту браузер с SuccessURL/FailURL production уходит не на этот внутренний адрес, а на публичный HTTPS-адрес staging из `PRIME_PAY_RELAY_PUBLIC_URL` (например, `https://primetime-showdown-staging.duckdns.org`; только доменное имя по https, без пути, без IP и localhost). Дальше staging сам отправляет игрока в свою игру (`PRIME_GAME_URL`). Если адрес не задан или не подходит — страница возврата без перенаправления. Пересылка ResultURL не меняется.
3. Демо-счета (≥ 7·10¹⁴) и боевые остаются на production. Повторная передача исключена (заголовок `X-Prime-Relay`, ответ 508); staging никогда не передаёт дальше.

Так staging продолжает работать при любой настройке production, а будущие боевые платежи приходят прямо на production — переключать адреса туда-обратно больше не нужно.

## 4. Как включить (на сервере, только по решению владельца; подробно — docs/RELEASE_1_8_8.md, этап Б)

Предварительно: сервер 1.8.8 развёрнут на production с выключенной оплатой; документы утверждены и опубликованы (`npm run legal:release -- --approved …`); репетиция на staging пройдена (раздел 6).

1. `/etc/primetime/robokassa.env`: `ROBOKASSA_MERCHANT_LOGIN=primetimeshowdown`, `ROBOKASSA_HASH_ALGORITHM=sha256`, `ROBOKASSA_TEST_PASSWORD_1`, `ROBOKASSA_TEST_PASSWORD_2` — **те же тестовые пароли, что на staging; боевых там быть не должно**. Права 640, root:pocketbase.
2. `/etc/primetime/pocketbase.env`: `PRIME_SERVER_ROLE=production`, `PRIME_PAY_MODE=demo`, `PRIME_DEMO_UNTIL=ГГГГ-ММ-ДД`, `PRIME_SHOP_SALES=open`, `PRIME_PAY_RELAY_URL=http://127.0.0.1:8091`.
3. Служба должна читать `robokassa.env` (строка `EnvironmentFile=-/etc/primetime/robokassa.env` в `deploy/linux/pocketbase.service`).
4. `sudo systemctl restart pocketbase` → в журнале: `PRIME: DEMONSTRATION payments (Robokassa TEST mode, no money moves, demo rights counted) until …` и `PRIME: test-range Robokassa notifications and returns are passed on to http://127.0.0.1:8091 …`; `sudo bash deploy/linux/prime-shop.sh status` → `mode: demo`, `ready: true`.
5. Кабинет Robokassa: адреса Result/Success/Fail → production (п. 3.1). Тестовые покупки на staging после этого идут через передачу.

## 5. Как закончить

- Само: после `PRIME_DEMO_UNTIL` оплата выключается, демо-права не учитываются.
- Вручную: `PRIME_PAY_MODE=` (пусто) и перезапуск; затем `sudo bash deploy/linux/prime-shop.sh demo-end` (отзывает демо-права, закрывает открытые демо-заказы; боевые права не трогает).
- Перед настоящими продажами: убрать тестовые пароли из `/etc/primetime/robokassa.env`, `demo-end`, затем включение `live` (docs/RELEASE_1_8_8.md, этап Г).

## 6. Репетиция на staging (обязательна до production)

Staging тоже может работать в режиме demo (роль staging допускается — именно для репетиции):

1. На staging: `PRIME_PAY_MODE=demo`, `PRIME_DEMO_UNTIL=<через неделю>`, тестовые пароли как сейчас; перезапуск **только** `pocketbase-staging`; адреса кабинета пока на staging.
2. Тестовая сборка игры, указывающая на staging (как в docs/ROBOKASSA_SETUP.md, шаг 5): покупка RAY за 99 ₽ на настоящей тестовой странице Robokassa → возврат → «Тестовая покупка подтверждена» → предмет в коллекции с пометкой «Тестовая покупка».
3. `prime-shop order <InvId>`: счёт ≥ 700 000 000 000 000, `env demo`, `fulfilled`; `prime-shop ledger` → `[demo, counted]`.
4. Вернуть staging в `PRIME_PAY_MODE=test` (демо-права перестанут учитываться), при желании `prime-shop demo-end`.

`npm run payments` (разделы «Демонстрация на официальном сайте…», «Одни адреса Robokassa…»): обязательный и ограниченный срок, боевой пароль рядом с демо → оплаты нет, тестовый режим на production по-прежнему запрещён, публичная конфигурация (env demo, цены, LUCIEN не продаётся), свои условия (редакция 9002), учёт только демо-прав, отказ на персонажа, счёт демо-диапазона и цена 49 ₽, `IsTest=1` и подпись тестовым паролем, свой журнал, отказ для `IsTest=0` и боевой подписи, SuccessURL ничего не выдаёт, подтверждение → право `demo`, повтор не дублирует, чужой (staging) счёт без передачи не принимается, после перехода на live демо-права не учитываются, `demo-end`; передача: тестовый счёт → staging без изменений и ответ staging, ничего не записано на production, демо/боевые не передаются, возврат игрока к staging, защита от петли, не-production не передаёт.
