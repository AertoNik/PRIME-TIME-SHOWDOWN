## 1. Как будет устроено (после Stage 2)

```
Игрок (телефон / компьютер)
   │  игра с GitHub Pages: https://aertonik.github.io/PRIME-TIME-SHOWDOWN/
   ▼
https://api.ВАШ-ДОМЕН          ← Caddy: HTTPS-сертификат Let's Encrypt, защита, закрытая панель
   ▼
127.0.0.1:8090                 ← PocketBase 0.40.5 (системный пользователь pocketbase)
   ▼
/var/lib/primetime/pb_data     ← база: аккаунты, профили, облачные сохранения, приглашения
/var/backups/primetime         ← ежедневные проверенные копии
```

- Игра на GitHub Pages остаётся статической страницей. Пароли, ключи и токены администратора в неё не попадают.
- В интернет смотрит только Caddy (порты 80 и 443). PocketBase слушает только сам сервер.
- Панель администратора PocketBase из интернета закрыта (ответ 404). Администратор открывает её через SSH-туннель.

## 2. Кто может зарегистрироваться

Решает **сервер**, а не игра. Переменная `PRIME_REGISTRATION` в настройках сервера:

| Значение | Что происходит |
|---|---|
| `invite_only` | **закрытая бета**: аккаунт можно создать только с кодом приглашения |
| `disabled` | новые аккаунты не создаются вообще; вход в существующие работает |
| `public` | открытая регистрация — **только после публичного запуска**, не сейчас |
| нет строки, опечатка (`Public`, `open`, `invite-only`…) | считается `disabled` — сервер по ошибке не откроется |

Игра узнаёт режим по адресу `/api/prime/config` и показывает нужный текст. Если ответ не пришёл, игра считает регистрацию закрытой.

Существующие аккаунты всегда входят **без** кода. Подтверждение email и восстановление пароля работают в любом режиме.

## 3. Окружения игры

| Окружение | Как включается | Сервер |
|---|---|---|
| гостевая игра | обычный `npm run build` (так сейчас собирает GitHub Pages) | никакого — ни кнопок, ни запросов, ни SDK |
| `local` | `npm run dev:accounts` на Mac | `http://127.0.0.1:8090` (`npm run backend`) |
| `beta` | `VITE_PRIME_ACCOUNTS=beta` + `VITE_PRIME_API_URL=https://…` в `.env.production` | сервер закрытой беты, только HTTPS |
| `production` | `VITE_PRIME_ACCOUNTS=production` + адрес | будущий публичный сервер, только HTTPS |

Образец — файл [`.env.example`](../.env.example). Всё, что начинается с `VITE_`, попадает в опубликованную игру и видно любому. Туда можно писать только адрес сервера, никаких паролей и ключей. Адрес без `https://` игра в beta/production не примет и покажет причину в PRIME ID.

**Пока `.env.production` не создан, GitHub Pages собирает гостевую игру — как раньше.** Создавать его — шаг Stage 2.

## 4. Что сделано в Stage 1

**Резервная копия вашей локальной базы** перед любыми изменениями:

- `backups-private/pb_data-2026-10-18_221817-before-1.8.2/` (и `.zip` рядом);
- проверена целостность, контрольные суммы совпадают;
- восстановление проверено на отдельной копии;
- исходная база не удалялась и не менялась.

**Закрытая бета по приглашениям** ([PRIME_CLOUD_INVITES.md](PRIME_CLOUD_INVITES.md)):

- коды на 130 случайных бит; в базе хранится только их хеш SHA-256;
- код одноразовый, действует 14 дней, его можно отозвать;
- проверка кода и создание аккаунта идут в одной транзакции: два человека с одним кодом не получат два аккаунта;
- коллекция `invites` закрыта для обычного API полностью;
- коды создаёт только консольная команда на самом сервере. Открытого адреса для генерации нет.

**Режимы регистрации** `disabled` / `invite_only` / `public` описаны выше.

**Окна в игре.** В PRIME ID появились:

- значок «CLOSED BETA»;
- текст для гостя;
- поле «Код приглашения»;
- понятные ошибки: неверный, использованный и истёкший код, регистрация закрыта.

Остальной вид PRIME ID не менялся.

**Страницы писем.** Ссылки из писем открывают свои страницы на сервере, `/auth/verify/` и `/auth/reset/`. Они на русском, со строгой CSP и с кнопкой возврата в игру.

**Безопасность браузера:**

- в `index.html` действует Content Security Policy: скрипты только из самой игры, без `eval` и встроенного кода;
- CORS разрешает только адрес GitHub Pages;
- лимиты частоты запросов: регистрация — 5 в минуту с одного адреса.

**Набор для VPS** в `deploy/linux/`. Он подготовлен, но на настоящем сервере не запускался:

| Файл | Что делает |
|---|---|
| `install.sh` | установка на чистую Ubuntu 24.04: пакеты, пользователь `pocketbase`, PocketBase с проверкой SHA-256, службы, Caddy, firewall |
| `pocketbase.service` | служба systemd: непривилегированный пользователь, только `127.0.0.1`, запись только в папку данных, автоперезапуск |
| `Caddyfile` | HTTPS, закрытая панель и служебные адреса администратора, лимит размера запроса, заголовки безопасности |
| `pocketbase.env.example` | шаблон настроек сервера без настоящих значений |
| `backup.sh`, `restore.sh`, `prime-backup.timer` | ежедневные проверенные копии, восстановление без удаления текущих данных |
| `update.sh` | обновление: сначала копия, при сбое — откат файлов |
| `healthcheck.sh` | быстрая проверка, что всё работает |
| `invites.sh` | приглашения на сервере |

**Архив для загрузки на сервер** — команда `npm run server:bundle`. Он содержит только код сервера, шаблоны и инструкции.

**Почта:**

- SMTP настраивается из файла настроек сервера;
- без `PRIME_MAIL_MODE=smtp` (и без тестовой почты на Mac) сервер писем не отправляет вовсе, а аккаунты закрытой беты подтверждает организатор вручную ([PRIME_BETA_PUBLISH.md](PRIME_BETA_PUBLISH.md));
- на Mac по-прежнему работает Mailpit.

**Проверка синхронизации при плохом интернете.** Проверены случаи:

- медленный ответ;
- ошибка сервера 503;
- сессия завершена на сервере;
- обрыв связи сразу после матча с перезагрузкой страницы.

Во всех случаях прогресс не терялся, и ревизия не задваивалась.

## 5. Чем проверено

```bash
npm run accounts               # 72 проверки без сервера: правила, коды, обычная и beta-сборка, набор для VPS
npm run backend:test           # 97 проверок 1.8.1 на настоящем PocketBase (временная база)
npm run beta:test              # 53 проверки закрытой беты на настоящем PocketBase (временная база)
npm run backend:migrate-check -- backups-private/pb_data-2026-10-18_221817-before-1.8.2
```

`beta:test` проверяет:

- все режимы регистрации, включая опечатки в настройке;
- 20 сценариев приглашений;
- попытки обойти приглашение через обычный API PocketBase;
- лимиты частоты;
- плохое соединение;
- копию при работающем сервере и восстановление;
- скрипты `backup.sh` и `restore.sh`;
- перенос базы на «другой сервер» с ключом шифрования и без него.

`migrate-check` применяет миграцию 1.8.2 к **временной копии** вашей резервной копии и сравнивает до и после. На вашей базе аккаунты, хеши паролей, никнеймы, сохранения и история не изменились.

Все тестовые данные искусственные. Временные базы удаляются после проверки.

## 6. Что НЕ проверено (честно)

- **Linux-сервер.** На этом Mac нет Linux, Docker и VPS. Поэтому `install.sh`, systemd, Caddy, ufw, `invites.sh` и `healthcheck.sh` проверены только чтением и `bash -n`, но не запуском на Ubuntu. `backup.sh` и `restore.sh` запускались на Mac. Первый запуск на VPS — часть Stage 2, его нужно делать внимательно, по шагам.
- **Настоящий HTTPS и домен.** Их нет.
- **Настоящая почта (SMTP).** Провайдер не выбран.
- **Внешние зашифрованные копии.** Место хранения не выбрано, скрипт готов.
- **iPhone и Android на настоящем сервере.** Проверялись только узкие окна браузера: 390, 375 и 320 px.
- **Нагрузка от многих игроков одновременно.**

## 7. Известные ограничения

- Бои считаются в браузере. Деньги, победы и прогресс в сохранении не доказывают, что игрок их честно заработал. Сервер проверяет формат, диапазоны и легальность колод, но настоящего античита нет. Для закрытой беты с друзьями это приемлемо, для мирового рейтинга — нет.
- При регистрации сервер сообщает «email уже занят». Так можно узнать, зарегистрирован ли адрес. Это ограничено лимитом 5 попыток в минуту.
- Ссылки в письмах работают, только если `PRIME_APP_URL` указывает на настоящий HTTPS-адрес сервера.
